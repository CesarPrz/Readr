# Readr

Appli mobile de recherche de livres (React Native + Expo) : recherche via l'API publique Open Library, fiche détail avec éditions/formats disponibles, et une bibliothèque personnelle organisée en listes de lecture ("À lire", "En cours", "Lu", "Aimés", et des listes perso), stockée localement pour l'accès hors-ligne. Depuis les Phases 1 et 2 du plan Firebase (doc Claude du projet), une connexion Firebase anonyme et silencieuse tourne en tâche de fond dès le premier lancement, et la bibliothèque/les listes sont sauvegardées vers Firestore au fil de l'eau (voir "Choix techniques" plus bas) — sans écran de compte ni rien à saisir. Depuis la section "Listes de lecture publiques", ces listes sont en **lecture publique** dans Firestore : n'importe quel utilisateur connecté peut voir la bibliothèque et les listes de n'importe qui (pas encore de navigation UI pour ça — voir "Choix techniques"). Depuis la Phase 3, l'utilisateur peut lier ce compte anonyme à Google — seul endroit de l'app où une connexion est proposée, et seule partie du projet qui nécessite un dev client plutôt qu'Expo Go (voir "Phase 3 : connexion Google" plus bas). Depuis "Profil fusionné" (07/10/2026), ce n'est plus un onglet Profil dédié : le profil (pseudo éditable, photo Google, connexion/déconnexion) s'affiche en en-tête de l'onglet "Ma bibliothèque" — voir "Choix techniques" plus bas. Depuis "Profil façon Instagram" (08/10/2026), cet en-tête reprend la mise en page d'un profil Instagram (avatar agrandi, compteurs Abonnés/Abonnements, bio éditable) ; les compteurs restent purement visuels pour l'instant (toujours à 0), aucun système de followers n'existe encore.

> ⚠️ **Important, si tu reviens sur ce projet après une pause :** `app.json` liste maintenant `@react-native-google-signin/google-signin` dans `plugins` (Phase 3). Si ce paquet n'est pas encore installé, **`npm start`/`expo start` va planter** (Expo résout tous les plugins listés même en Expo Go, voir le paragraphe "Config plugins" du `CLAUDE.md` — déjà arrivé deux fois sur ce projet pour d'autres paquets). Lance `npx expo install @react-native-google-signin/google-signin` avant ton prochain `npm start`, que tu comptes travailler sur la Phase 3 tout de suite ou non.
>
> ⚠️ **Autre point si tes projets Firebase (dev et/ou prod) étaient déjà configurés avant "Listes de lecture publiques" :** les règles Firestore ont changé (lecture désormais publique). Recolle le contenu de `firestore.rules` dans Firebase Console → Firestore Database → Règles, dans CHACUN des deux projets — l'ancienne version (lecture restreinte au propriétaire) reste sinon active côté console.
>
> ⚠️ **Idem si tes projets étaient configurés avant "Profil fusionné" (07/10/2026) :** `firestore.rules` a gagné une nouvelle règle pour `users/{uid}` (pseudo/photo public). Recolle le fichier à jour (ou `firebase deploy --only firestore:rules` si la CLI est déjà en place, voir "Recommandations collaboratives" plus bas) dans les deux projets — sans ça, l'édition du pseudo/la photo échouent silencieusement (best-effort, l'app reste utilisable).

## Démarrer

Depuis ce dossier, en local (Node ≥ 18) :

```bash
npm install
npx expo install --fix   # aligne les versions natives sur le SDK Expo installé
npx expo install expo-camera   # ajoute le scanner de code-barres (une fois, à la bonne version)
cp env.dev.example .env.dev   # puis remplis .env.dev (voir "Environnements" plus bas)
npm run start:dev             # active l'environnement dev et lance Expo
```

Scanne le QR code avec l'app **Expo Go** (iOS/Android) pour lancer l'appli sans build natif.

> **Clé API Google Books** : le repli `findByIsbn` du scanner (voir plus bas) utilise l'API Google Books, qui exige une clé même en lecture seule. Sans clé configurée, ce repli est silencieusement sauté (pas d'erreur) — le scanner reste fonctionnel, juste avec moins de couvertures pour les livres absents d'Open Library.

> **Config Firebase** : la connexion anonyme silencieuse (voir "Choix techniques") a besoin des six variables `EXPO_PUBLIC_FIREBASE_*` (config de l'app Web du projet Firebase, dans la Firebase Console) et de l'activation manuelle du fournisseur "Anonymous" (Authentication → Sign-in method). Sans ça, `ensureSignedIn` échoue silencieusement au démarrage — l'app reste par ailleurs pleinement utilisable, cette connexion ne bloque rien. Voir "Environnements (dev / prod)" ci-dessous pour la marche à suivre complète.

> Les fichiers ont été générés hors ligne (pas d'accès au registre npm depuis l'environnement qui les a écrits), donc les versions de dépendances dans `package.json` sont volontairement larges. `npx expo install --fix` corrige automatiquement toute incohérence de version avant le premier lancement.

## Environnements (dev / prod)

Deux projets Firebase séparés, pour ne jamais mélanger les données de test avec l'usage réel de l'app :

- **dev** — pour développer/tester : utilisateurs anonymes de test, données jetables.
- **prod** — pour ton usage réel de l'app : données à garder.

### Mettre en place le projet dev (si pas déjà fait)

1. `cp env.dev.example .env.dev`
2. Dans la [Firebase Console](https://console.firebase.google.com), ouvre ton projet Firebase existant → Paramètres du projet → Général → "Vos applications" → application Web (icône `</>`) — crée-en une si besoin (pas d'Hosting à activer) — copie les six valeurs dans `.env.dev`.
3. Authentication → Sign-in method → active le fournisseur **Anonymous**.
4. Firestore Database → **Créer une base de données** (mode production, la région n'a pas d'importance pour un usage perso) → onglet **Règles** → colle le contenu de `firestore.rules` (à la racine du dépôt) → Publier. Sans cette étape, la sauvegarde cloud de la bibliothèque (Phase 2) échoue silencieusement — l'app reste utilisable, juste sans sauvegarde.
5. `npm run env:dev` (ou directement `npm run start:dev`).

### Mettre en place le projet prod

1. Dans la Firebase Console → **Ajouter un projet** → un nouveau projet, distinct du projet dev (ex. renommer mentalement l'existant "readr-dev" et le nouveau "readr-prod" pour s'y retrouver).
2. Mêmes étapes que ci-dessus dans ce nouveau projet : application Web pour récupérer sa config, fournisseur Anonymous, **et** base Firestore + règles (`firestore.rules`) — les quatre étapes de la section dev, à refaire ici.
3. `cp env.prod.example .env.prod`, puis colle les valeurs de ce nouveau projet dedans.
4. `npm run env:prod` (ou `npm run start:prod`).

### Basculer entre les deux au quotidien

```bash
npm run env:dev     # ou : npm run start:dev  (bascule + lance Expo directement)
npm run env:prod    # ou : npm run start:prod
```

`npm run env:*` copie `.env.dev`/`.env.prod` vers `.env` — le seul fichier qu'Expo charge réellement. Ne remplis jamais `.env` à la main : il est régénéré à chaque bascule, toute modification directe serait écrasée. `EXPO_PUBLIC_APP_ENV` (présent dans les deux fichiers) s'affiche dans la console Metro/Expo Go au démarrage, avec l'identifiant du projet Firebase actif — un repère rapide pour vérifier qu'on n'est pas sur le mauvais projet avant de tester quoi que ce soit.

`.env.dev` et `.env.prod` ne sont jamais commités (voir `.gitignore`) ; `env.dev.example`/`env.prod.example` sont les templates versionnés. Voir aussi "Choix techniques" plus bas pour le détail (pourquoi un script maison plutôt que le mécanisme `NODE_ENV` intégré d'Expo).

## Phase 3 : connexion Google (nécessite un dev client)

**Pourquoi pas Expo Go ici, alors que tout le reste du projet l'utilise ?** Recherche documentée (sept. 2026) : la doc Expo actuelle exclut explicitement Expo Go pour tout flux OAuth ("Expo Go cannot be used for local development and testing of OAuth or OpenID Connect-enabled apps due to the inability to customize your app scheme"), et l'ancien contournement (`expo-auth-session/providers/google` + proxy `auth.expo.io`) a été entièrement retiré du SDK en 2023. Décision pour ce projet : la Phase 3 seule utilise un **dev client local** (`npx expo prebuild` + `npx expo run:android`/`run:ios`) — jamais le service cloud EAS Build. Tout le reste (Phases 1, 2, 4+, écrans existants) continue de tourner en Expo Go classique (`npm start`), sans rien à changer.

### Mise en place, par environnement (dev puis, plus tard, prod)

1. **Installer la lib** (une seule fois, avant même ton prochain `npm start` — voir l'avertissement en haut de ce README) :
   ```bash
   npx expo install @react-native-google-signin/google-signin
   ```
2. **Activer Google comme fournisseur** : Firebase Console (projet dev) → Authentication → Sign-in method → **Google** → activer. Juste en dessous, sous "Web SDK configuration", copie le **"Web client ID"** dans `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` de `.env.dev` (voir `env.dev.example`) — ce n'est pas le client Android ni iOS, malgré le nom.
3. **Télécharger les fichiers de config natifs**, toujours depuis ce même projet Firebase (Paramètres du projet → Général → tes apps Android/iOS — crée-les ici si elles n'existent pas encore, avec le `package`/`bundleIdentifier` de `app.json`, `com.cesar.readr`) :
   - `google-services.json` → renomme-le **`google-services.dev.json`**, à la racine du dépôt.
   - `GoogleService-Info.plist` → renomme-le **`GoogleService-Info.dev.plist`**, à la racine du dépôt.
   - Pour l'app **Android**, Firebase demande une empreinte SHA-1 : récupère-la avec `cd android && ./gradlew signingReport` (après un premier `npx expo prebuild`) et colle-la dans les paramètres de l'app Android sur Firebase Console — sans ça, `GoogleSignin.signIn()` échoue côté Android même avec le reste bien configuré.
4. **Activer l'environnement dev** (bascule maintenant aussi les fichiers Google, en plus de `.env`) :
   ```bash
   npm run env:dev
   ```
5. **Générer le projet natif et lancer le dev client** :
   ```bash
   npm run prebuild            # npx expo prebuild --clean — régénère android/ et ios/ à partir de app.json
   npm run devclient:android:dev   # ou : npm run devclient:ios:dev (nécessite un Mac)
   ```
   Ces deux commandes remplacent `expo start`/Expo Go **pour cette phase uniquement** — elles compilent et installent un vrai build de l'app (émulateur ou appareil connecté). Peut prendre plusieurs minutes la première fois (installation des dépendances natives Gradle/CocoaPods).
6. Une fois lancé, onglet **Profil** → "Se connecter avec Google". Vérifie ensuite, dans Firebase Console → Authentication → Users, que l'utilisateur anonyme existant a bien un e-mail Google associé (même `uid`, pas un nouvel utilisateur) — c'est le signe que la liaison (`linkWithCredential`, pas une nouvelle connexion) a fonctionné plutôt qu'une reconnexion depuis zéro.

**Pour le projet prod**, refaire les étapes 2 et 3 dans le second projet Firebase, en nommant les fichiers `google-services.prod.json` / `GoogleService-Info.prod.plist` / `.env.prod`, puis `npm run env:prod` + `npm run prebuild` + `npm run devclient:android:prod` (ou `:ios:prod`).

**Windows sans Mac** : `npx expo run:ios` n'est pas exécutable en local (nécessite Xcode). La configuration iOS (plugin, `GoogleService-Info.plist`) peut être préparée dès maintenant, mais son test réel attend un Mac (le tien, un service de build cloud type EAS Build si la contrainte "pas d'EAS Build" est reconsidérée un jour, ou une location ponctuelle) — l'Android peut avancer indépendamment en attendant.

**Après un changement d'environnement (`npm run env:dev`/`env:prod`)**, si tu utilises déjà le dev client, relance `npm run prebuild` avant de relancer `devclient:android:*`/`devclient:ios:*` : contrairement à `.env` (relu à chaque redémarrage Metro), `google-services.json`/`GoogleService-Info.plist` sont copiés dans le projet natif par `expo prebuild`, pas relus dynamiquement.

**`INSTALL_FAILED_INSUFFICIENT_STORAGE` à l'install sur l'émulateur/appareil (06/10/2026)** : `npm run devclient:android:dev`/`:prod` désinstallent désormais automatiquement l'ancien build (`scripts/clean-android-install.js`, `adb uninstall`) avant chaque réinstallation — plus besoin de le faire à la main depuis les Paramètres de l'appareil. Ça suffit dans la grande majorité des cas (chaque build de debug laissait l'ancienne APK + ses données occuper de la place, qui finissait par remplir le petit stockage interne par défaut d'un émulateur). Si l'erreur persiste malgré ça, le disque de l'émulateur est probablement trop petit dans l'absolu : Android Studio → Device Manager → crayon d'édition sur l'AVD → "Show Advanced Settings" → augmenter "Internal Storage" (ex. 2 Go → 8 Go) → "Wipe Data" une fois — réglage définitif, à faire une seule fois par AVD.

**Si le compte Google est déjà lié à un autre utilisateur Firebase** (`auth/credential-already-in-use` — app réinstallée, ou compte déjà utilisé sur un autre appareil), l'app **bascule automatiquement dessus** : la session anonyme courante est abandonnée, et la bibliothèque/les listes de ce compte existant sont restaurées depuis Firestore sur cet appareil (une alerte "Compte retrouvé" le confirme à l'écran). **Ce qui n'est toujours pas géré** (voir le plan Firebase, doc Claude du projet) : la fusion des deux bibliothèques — celle de la session anonyme abandonnée est purement et simplement écrasée par celle du compte existant, décision produit assumée.

## Recommandations collaboratives (Cloud Functions)

**Première brique du projet à utiliser des Cloud Functions** — jusqu'ici tout tournait sans Firebase CLI (connexion/Firestore/Auth passent par le SDK JS modulaire côté app, et `firestore.rules` se collait manuellement dans la Console). Les Cloud Functions nécessitent un vrai outillage côté machine de dev : Firebase CLI, Node.js, un compte facturation Blaze sur CHAQUE projet Firebase (dev et prod) — l'usage réel de cette fonctionnalité reste dans le quota toujours-gratuit de Blaze à cette échelle, mais Google exige une carte bancaire enregistrée pour activer Blaze, même si rien n'est jamais facturé.

### Mise en place (une fois, par environnement dev puis prod)

1. **Passer le projet Firebase en formule Blaze** : Firebase Console (projet concerné) → en bas à gauche, "Modifier le forfait" → Blaze (paiement à l'usage). Nécessaire même pour rester à 0 € — Spark ne permet pas du tout les Cloud Functions.
2. **Installer la Firebase CLI** (une seule fois sur ta machine) :
   ```bash
   npm install -g firebase-tools
   firebase login
   ```
3. **Relier ce dossier aux deux projets Firebase**, à la racine du dépôt (crée `.firebaserc`, pas encore présent — jamais généré par ce projet jusqu'ici) :
   ```bash
   firebase use --add
   ```
   Choisis le projet dev, donne-lui l'alias `dev` ; relance la commande pour le projet prod avec l'alias `prod`. `firebase use dev`/`firebase use prod` bascule ensuite entre les deux, à ne pas confondre avec `npm run env:dev`/`env:prod` (qui bascule les fichiers `.env`/`google-services.*` de l'app, pas le projet ciblé par la CLI — penser à faire les deux bascules ensemble).
4. **Installer les dépendances des Cloud Functions** (dossier séparé, son propre `package.json` — jamais mélangé aux dépendances de l'app React Native) :
   ```bash
   cd functions
   npm install
   cp .env.example .env    # puis mets une vraie valeur pour RECOMPUTE_SECRET (test manuel seulement, voir plus bas)
   cd ..
   ```
5. **Déployer** (Firestore use le projet actif choisi à l'étape 3) :
   ```bash
   firebase deploy --only functions
   ```
   Ça déploie `scheduledRecomputeBookStats` (planifiée, une fois par jour) et `recomputeBookStatsManually` (déclenchement HTTP manuel, pour tester sans attendre). Répéter pour l'autre environnement (`firebase use prod` puis `firebase deploy --only functions`).
6. **`firestore.rules` est maintenant aussi déployable par la CLI** (nouveauté permise par cette mise en place, voir le fichier lui-même) : `firebase deploy --only firestore:rules`, en plus de — ou à la place de — le copier-coller manuel dans la Console pratiqué jusqu'ici pour les deux projets.

### Tester sans attendre le passage planifié

La fonction planifiée tourne une fois par jour — pour vérifier que le calcul fonctionne tout de suite après l'avoir déployé (ou après avoir ajouté des livres "aimés" de test sur deux comptes différents, la co-occurrence ne comptant jamais à l'intérieur d'un seul compte) :
```bash
curl "https://<région>-<id-projet>.cloudfunctions.net/recomputeBookStatsManually?secret=<RECOMPUTE_SECRET>"
```
L'URL exacte (région + id de projet) s'affiche dans le terminal à la fin de `firebase deploy`, et reste consultable dans Firebase Console → Functions. La réponse JSON indique combien d'utilisateurs et de livres ont été pris en compte — `{"usersConsidered":0,...}` signifie qu'aucun utilisateur n'a encore de livre "aimé"/"lu" à cette date dans cet environnement (normal tant que le projet dev ne contient que peu de données de test).

### Ce que ça ajoute côté app

`domain/repositories/BookStatsRepository.ts` (nouveau port) + `data/firebase/FirestoreBookStatsRepository.ts` (implémentation, lit `bookStats/{bookId}`) sont utilisés par `getRecommendations` pour générer jusqu'à 2 rows "Les lecteurs qui ont aimé/lu X ont aussi aimé" sur Découvrir — voir "Choix techniques" ci-dessous pour le détail complet du nouvel ordre des rows. Aucune Cloud Function n'est appelée directement depuis l'app : le client ne fait que LIRE le résultat déjà calculé (`getDoc`, une lecture par livre consulté), jamais de calcul ni d'agrégation côté téléphone.

## Structure (Clean Architecture + Redux)

- `src/domain/` — cœur métier, aucune dépendance à React Native, Redux ou Open Library
  - `entities/` — `Book`, `Edition`, `BookDetail` (dont `subjects`, les sujets Open Library bruts), `LibraryEntry` (dont `listIds: string[]`, voir `ReadingList`), `ReadingList` (liste de lecture, générique — 4 par défaut + listes perso, voir "Choix techniques"), `RecommendationGroup`, `UserProfile` (identité Firebase Auth courante, plus `username?: string` depuis "Profil fusionné" — pseudo public éditable, voir "Choix techniques")
  - `repositories/` — interfaces `BookRepository` / `LibraryRepository` / `ListRepository` / `AuthRepository` (dont `linkWithGoogle`/`signOutCurrentUser`, Phase 3) / `GoogleIdentityProvider` (Phase 3) / `LibrarySyncRepository` / `ListSyncRepository` / `BookStatsRepository` (recommandations collaboratives, voir "Choix techniques") / `UserProfileRepository` ("Profil fusionné") (ports)
  - `usecases/` — `searchBooks`, `searchBooksInLanguage`, `findBookByIsbn`, `getBookDetail`, `loadLibrary`, `addBookToLibrary`, `removeBookFromLibrary`, `updateLibraryEntry`, `toggleBookList`, `getRecommendations`, `ensureSignedIn`, `syncLibraryEntry`, `removeLibraryEntryFromCloud`, `syncLibraryToCloud`, `linkGoogleAccount`, `signOutUser`, `seedDefaultLists`, `createReadingList`, `renameReadingList`, `deleteReadingList`, `syncListEntry`, `syncListsToCloud`, `removeListFromCloud`, `loadUserProfile`, `updateUsername`, `syncProfilePhotoToCloud`
- `src/data/` — implémentations concrètes des ports du domain
  - `openLibrary/` — `OpenLibraryBookRepository` (appels HTTP + mapping vers les entités du domain)
  - `googleBooks/` — repli de `findByIsbn` (clé API requise, voir "Environnements" plus haut), utilisé quand Open Library (index + catalogue) ne trouve rien ; seule source de repli à fournir une couverture (`Book.coverUrl`)
  - `bnf/` — dernier recours de `findByIsbn`, après Google Books (pas de repository à part entière, juste un client + mapping utilisés en interne par `OpenLibraryBookRepository`)
  - `local/` — `AsyncStorageLibraryRepository` (bibliothèque locale persistée, migre les anciennes entrées `status`/`liked`) + `AsyncStorageListRepository` (listes de lecture)
  - `firebase/` — `FirebaseAuthRepository` (connexion anonyme, liaison Google, déconnexion) + `FirestoreLibraryRepository` (sauvegarde cloud de la bibliothèque) + `FirestoreListRepository` (sauvegarde cloud des listes) + `FirestoreBookStatsRepository` (lecture des recommandations collaboratives précalculées) + `FirestoreUserProfileRepository` (pseudo/photo public, "Profil fusionné") — SDK JS modulaire Firebase, voir "Choix techniques"
  - `google/` — `GoogleSignInProvider` (Phase 3, lib native — seul module qui ne tourne pas dans Expo Go, voir "Phase 3 : connexion Google")
- `src/composition/repositories.ts` — seul fichier qui instancie les implémentations concrètes ; tout le reste dépend des interfaces du domain
- `src/store/` — state management Redux Toolkit : `librarySlice`, `listsSlice`, `searchSlice`, `languageResultsSlice`, `bookDetailSlice`, `discoverSlice`, `scanSlice`, `authSlice` (thunks qui appellent les usecases, dont `linkGoogleAccount`/`signOutUser`/`loadUserProfile`/`updateUsername`), `store.ts`, `hooks.ts` (`useAppDispatch`/`useAppSelector`)
- `src/theme/` — couleurs, espacements, typographie (thème sombre inspiré de la référence UI)
- `src/utils/` — helpers de présentation partagés entre écrans, sans dépendance à Redux/API (`languageLabels.ts`, `anonymousPseudonym.ts` — pseudonyme de repli du profil anonyme ; `genreLabels.ts` — genres usuels reconnus pour Découvrir ; `generateId.ts` — ids de listes perso)
- `src/navigation/` — barre d'onglets, **quatre depuis "Profil fusionné" (07/10/2026)** : Recherche / Scanner / Découvrir / Ma bibliothèque — plus de cinquième onglet Profil, voir "Choix techniques" — + piles de navigation
- `src/screens/` — Recherche, Résultats par langue, Scanner, Découvrir, Fiche livre, Ma bibliothèque (listes dynamiques + en-tête de profil depuis "Profil fusionné", voir "Choix techniques") — branchées sur le store Redux, plus d'appel direct à l'API ou à AsyncStorage
- `src/components/` — carte livre, badge de format, étoiles de notation, sélecteur de statut, carrousel de couvertures, en-tête de profil (`ProfileHeader`, "Profil fusionné") (purement présentationnels)

- `functions/` — **Cloud Functions, projet Node.js séparé** (son propre `package.json`/`tsconfig.json`, jamais mélangé aux dépendances de l'app React Native) : `src/recomputeBookStats.ts` (calcul des recommandations collaboratives) + `src/index.ts` (`scheduledRecomputeBookStats`, `recomputeBookStatsManually`) — voir "Recommandations collaboratives (Cloud Functions)" plus haut pour la mise en place et le déploiement.

Sens de dépendance : `screens/` et `store/` → `domain/` (interfaces) ; `data/` → implémente `domain/` ; `composition/` relie les deux. Aucun écran n'importe `data/` directement. `functions/` est hors de ce graphe : c'est un codebase à part, qui ne lit/écrit Firestore que via le SDK Admin, jamais via les ports `domain/`.

`src/api/` et `src/storage/` (l'ancienne implémentation Context + appels directs) sont obsolètes et vidés de leur contenu — à supprimer manuellement, rien ne les importe plus.

## Choix techniques (vs. le cahier des charges initial)

- **Redux Toolkit** pour le state partagé (bibliothèque, recherche, détail livre) organisé en **Clean Architecture** (domain / data / composition), à la demande explicite du porteur du projet — remplace le Context + AsyncStorage fait maison de la première version.
- **FlatList** plutôt que FlashList : moins de dépendances tierces à faire correspondre à la main sans pouvoir tester l'installation depuis l'environnement de génération initial. Fonctionnellement équivalent pour ce volume de données ; migrable plus tard si besoin de perf sur de très longues listes.
- Aucune donnée d'audiobook commercial (type Audible) n'existe en accès public : l'appli affiche un badge « disponible en édition audio » uniquement quand Open Library référence un format audio, sans lecteur ni lien d'achat.
- **Découvrir** affiche plusieurs rows de recommandations, chacune avec sa propre justification plutôt qu'une seule liste mélangée (`getRecommendations`, qui renvoie des `RecommendationGroup[]` — voir `domain/entities/RecommendationGroup.ts`), dans cet ordre : jusqu'à 2 rows **collaboratives** "Les lecteurs qui ont aimé/lu X ont aussi aimé" (voir "Recommandations collaboratives" plus bas), jusqu'à 2 rows "Car vous avez lu X (et Y)" (par auteur, à partir des livres au statut "lu"), jusqu'à 2 rows "Car vous avez aimé X (et Y)" (par auteur, à partir des livres `liked`), et au plus une row "D'autres livres du genre <genre>" basée sur un genre usuel reconnu (Horreur, Policier, Romance, Fantasy, Biographie...) parmi les sujets Open Library (`BookDetail.subjects`) du livre lu ou aimé le plus récent — voir "Genre reconnu parmi une liste usuelle" ci-dessous. Un même auteur n'est jamais recommandé pour deux raisons différentes ("lu" prioritaire sur "aimé"), et un même LIVRE n'apparaît jamais dans deux rows différentes, quelle que soit leur origine (ensemble d'exclusion qui grossit au fil des rows générées, voir `getRecommendations`). Les rows par auteur/genre relancent une recherche Open Library et excluent les livres déjà dans la bibliothèque ; une row sans aucun nouveau résultat n'est simplement pas affichée. Recalculé à chaque ajout/retrait dans la bibliothèque.
- **Recommandations collaboratives (Cloud Functions, 06/10/2026)** : nouvelle brique "Les lecteurs qui ont aimé/lu X ont aussi aimé Y", calculée côté serveur plutôt que par l'app — la première fonctionnalité du projet à utiliser des **Cloud Functions**, voir `functions/` et la section dédiée plus bas pour l'installation/le déploiement. Principe : une Cloud Function planifiée (`scheduledRecomputeBookStats`, une fois par jour) parcourt les bibliothèques "aimées"/"lues" de TOUS les utilisateurs (déjà publiques en lecture depuis "Listes de lecture publiques" — pas de nouvelle règle de lecture nécessaire côté `users/{uid}/library`), compte les co-occurrences entre livres qu'une même personne a aimés/lus, et écrit pour chaque livre concerné ses quelques livres les plus souvent associés dans une nouvelle collection publique en lecture, privée en écriture côté client : `bookStats/{bookId}` (voir `firestore.rules`). Côté app, `BookStatsRepository`/`FirestoreBookStatsRepository` (nouveau port + implémentation, `domain/repositories/`, `data/firebase/`) lisent un seul document par livre consulté — aucun calcul ni agrégation côté client, juste une lecture d'un résultat déjà prêt. Permet d'obtenir l'essentiel de ce que la Phase 7 ("Recommandations sociales", voir le plan Firebase) visait, SANS attendre la Phase 4 ("Amis") : la donnée publique existe déjà, donc "les lecteurs" ici veut dire "tous les utilisateurs de l'app", pas spécifiquement "tes amis" — nuance assumée, voir le plan pour la discussion complète.
  - **Genre reconnu parmi une liste usuelle (07/10/2026, demande explicite du porteur du projet)** : les sujets Open Library sont une liste libre (mélange de genres, thèmes, lieux, prix littéraires...), pas une taxonomie de genres propre — l'ancien comportement (`subjects[0]` affiché tel quel, sans aucun filtre) avait fini par afficher littéralement *"D'autres classiques du genre 'Holes'"* (le titre d'un autre roman, catalogué comme sujet par Open Library, pas un genre du tout). `matchKnownGenre` (`src/utils/genreLabels.ts`) compare désormais CHAQUE sujet du livre à une liste fermée d'une quinzaine de genres usuels (Horreur, Policier, Thriller, Romance, Fantasy, Science-fiction, Biographie, Historique, Aventure, Jeunesse, Poésie, Humour, Classiques — par sous-chaîne, mots-clés en anglais ET en français), et retient le premier sujet qui correspond à l'un d'eux, dans l'ordre où Open Library les renvoie. Le libellé affiché est traduit en français (ex. "Policier"), mais la requête Open Library (`subject:"..."`) utilise le sujet brut qui a servi à la correspondance (ex. "Detective and mystery stories") — Open Library n'indexe pas ses sujets en français, interroger le libellé traduit ne renverrait rien. Aucun groupe "genre" n'est généré si aucun sujet du livre ne correspond à un genre connu, plutôt que d'en afficher un avec un libellé qui n'a jamais été un genre — heuristique toujours approximative (un livre peut très bien n'avoir aucun sujet reconnu, ou en avoir un qui ne reflète pas son genre principal), mais qui ne peut plus afficher n'importe quoi.
- **Regroupement des doublons de recherche** : Open Library indexe souvent le même livre sous plusieurs fiches "work" distinctes (doublons de catalogage, traductions non reliées à l'œuvre d'origine), ce qui faisait apparaître un même livre plusieurs fois dans les résultats. `docsToBooks` (dans `data/openLibrary/mappers.ts`) regroupe les résultats d'une page par titre + premier auteur normalisés, fusionne leurs identifiants d'œuvre et leurs langues, et la fiche détail agrège ensuite éditions/langues de tous les identifiants fusionnés (`BookRepository.getDetail` prend un tableau d'identifiants). Heuristique, pas une garantie : le regroupement ne se fait qu'au sein d'une page de résultats, jamais entre plusieurs pages, et deux livres différents partageant exactement un titre et un premier auteur seraient (rarement) fusionnés à tort.
  - **Choix de la couverture** : pour un groupe fusionné, `pickCoverId` retient la couverture de la fiche dont `first_publish_year` est le plus récent, plutôt que la première couverture rencontrée. Motivation : pour les classiques du domaine public, la couverture "par défaut" que renvoie Open Library est très souvent celle de la toute première édition numérisée, qui ne ressemble à aucune édition courante. Heuristique faible et non garantie — `first_publish_year` reste un champ par fiche "œuvre" de l'index de recherche, pas l'année précise de l'édition d'où vient la couverture — mais un biais vers le plus récent du groupe est préférable à un choix arbitraire, sans appel réseau supplémentaire. Les couvertures elles-mêmes restent celles qu'Open Library a scannées : pour beaucoup de classiques, aucune édition récente n'a de couverture référencée du tout, auquel cas ce choix ne change rien.
- **Liste "Aimés" et bulle cœur** : "Aimés" est une des 4 listes par défaut (`DEFAULT_LIST_IDS.liked`, voir "Listes de lecture publiques" plus bas), indépendante du statut de lecture — un livre "à lire" peut très bien être aussi dans "Aimés". Sur la fiche livre, une bulle en forme de cœur (coin haut-droit de la couverture) bascule cette appartenance (`toggleBookList`) ; si le livre n'est pas encore dans la bibliothèque, appuyer dessus l'y ajoute directement dans "Aimés" plutôt que d'obliger à d'abord passer par "Ajouter à ma bibliothèque" — un livre non ajouté ne peut pas figurer dans une liste.
- **Ordre de la fiche livre** : le résumé est affiché juste après le titre/auteur (et le badge audio éventuel), avant le bouton d'ajout et les contrôles de statut/note/notes personnelles — pour permettre de se décider à la lecture du résumé avant de choisir une liste. Les éditeurs et langues disponibles restent en bas de fiche.
- **Éditeurs plutôt que formats sur la fiche livre** : la section "Éditions disponibles" (badges de format par édition) a été remplacée par "Éditeurs" — une liste des éditeurs connus (`Edition.publisher`, tiré de `publishers[0]` côté Open Library), dédupliqués et affichés en texte simple, comme la liste des langues. Beaucoup d'éditions n'ont pas d'éditeur renseigné : dans ce cas, un texte de repli s'affiche ("Aucun éditeur référencé pour ce livre.") plutôt que rien du tout. Le résumé a le même traitement : quand Open Library n'a pas de description pour l'œuvre (fréquent pour certains titres, ex. *Les Thanatonautes* de Bernard Werber), un texte de repli s'affiche plutôt que de faire disparaître silencieusement toute la section "Résumé".
- **Couvertures multiples sur la fiche livre** : les éditions fusionnées d'un même livre (voir regroupement des doublons ci-dessous) peuvent chacune référencer une couverture différente — `Edition.coverId` porte désormais cette info (`data/openLibrary/mappers.ts`). `BookDetailScreen` construit la liste des couvertures connues (`presetCoverUrl` en premier s'il existe, puis `presetCoverId`, puis celles des éditions chargées, dédupliquées) et les passe à `CoverCarousel`, qui affiche une image statique s'il n'y en a qu'une, ou un carrousel swipable avec indicateurs à points sinon. Composant purement présentationnel : reçoit des URLs déjà résolues, jamais de `coverId` ni d'appel à `bookRepository`.
- **Deux représentations de couverture sur `Book`/`LibraryEntry`** : `coverId?: number` suit le schéma numérique d'Open Library (résolu en URL via `bookRepository.coverUrl(id, taille)`) ; `coverUrl?: string` porte une URL déjà résolue, pour les sources qui n'ont pas d'identifiant Open Library (ex. Google Books). Partout où une couverture est affichée, la règle est `book.coverUrl ?? bookRepository.coverUrl(book.coverId, taille)` — `coverUrl` est prioritaire quand il existe.
- **Résumé de repli venu de Google Books** : `getDetail`/`fetchBookDetail` n'enrichissent un livre qu'à partir d'une vraie fiche "œuvre" Open Library — pour un livre trouvé via le repli Google Books (`data/googleBooks/`, pas de fiche "œuvre" associée), ce résumé Open Library n'arrivera jamais. `Book.description` porte donc, comme `coverUrl`, un résumé déjà connu au moment où le livre est trouvé (le champ `description` du volume Google Books). `BookDetailScreen` garde le résumé Open Library prioritaire quand il existe (généralement plus complet/à jour), et ne retombe sur `presetDescription` que s'il n'y en a pas — sinon un livre venu de Google Books n'aurait jamais de résumé du tout, même quand Google Books en avait un.
  - **Et pour les livres bien référencés sur Open Library mais sans résumé ?** Cas distinct du précédent : l'œuvre existe bien chez Open Library (éditions, couvertures...) mais son champ `description` est simplement vide — constaté en pratique sur *Les Thanatonautes* de Bernard Werber, malgré 4 éditions connues. `OpenLibraryBookRepository.getDetail` retente alors Google Books, cette fois par titre + premier auteur (`findDescriptionOnGoogleBooks`, dans `data/googleBooks/googleBooksClient.ts`) puisqu'on n'a pas d'ISBN à ce stade — seulement les métadonnées de la fiche "œuvre" déjà chargée. Recherche par titre/auteur, meilleure correspondance seulement : moins fiable qu'une recherche par ISBN, mais suffisant pour un résumé (contrairement à une couverture ou une édition, un résumé légèrement décalé entre éditions reste presque toujours correct). Nécessite la même clé API que les autres replis Google Books ; sans clé, sauté silencieusement.
- **Connexion Firebase anonyme et silencieuse (Phase 1 du plan Firebase)** : `ensureSignedIn` (dispatché une fois au démarrage dans `App.tsx`) crée une identité Firebase Auth anonyme au tout premier lancement, sans le moindre écran — fondation pour la sauvegarde cloud et les fonctionnalités sociales à venir (voir le plan, doc Claude du projet), pas encore branchée à quoi que ce soit de visible. SDK JS modulaire (`firebase`, pas `@react-native-firebase`) pour rester compatible Expo Go, avec persistance de session via `initializeAuth` + `getReactNativePersistence(AsyncStorage)` (sans quoi la session ne survivrait pas à un redémarrage de l'app). `FirebaseAuthRepository` attend le premier `onAuthStateChanged` avant de décider de créer un nouvel utilisateur anonyme, pour ne pas en recréer un (et perdre le précédent) à chaque démarrage pendant que la session persistée se restaure de façon asynchrone. - **Sauvegarde cloud de la bibliothèque (Phase 2 du plan Firebase)** : chaque ajout/changement de listes/note/suppression sur la bibliothèque est répliqué vers Firestore (`users/{uid}/library/{bookId}`) juste après l'écriture locale, en tâche de fond et sans jamais bloquer l'UI (`librarySlice` appelle le usecase de sync sans l'attendre) — un passage `syncLibraryToCloud` au démarrage couvre aussi les entrées ajoutées avant l'existence de cette phase. À sens unique et best-effort côté écriture : toute erreur (hors ligne, base Firestore pas encore créée côté console) est avalée silencieusement plutôt que remontée à l'utilisateur. `title`/`authors`/`coverId`/`coverUrl`/`listIds`/`rating`/`note`/`updatedAt` sont synchronisés (`note` a rejoint cette liste avec "Listes de lecture publiques" ci-dessous — elle n'était PAS synchronisée à l'origine). Nécessite `initializeFirestore(app, { experimentalAutoDetectLongPolling: true })` plutôt que `getFirestore` seul (le transport de streaming par défaut de Firestore est peu fiable sur React Native), et une base Firestore + les règles de `firestore.rules` créées manuellement dans chaque projet (voir "Environnements" plus haut) — sans ça, la sauvegarde échoue silencieusement, sans affecter le reste de l'app. **À l'origine de cette phase, le local (AsyncStorage) restait l'unique source de vérité et l'app ne restaurait jamais sa bibliothèque depuis le cloud — ce n'est plus le cas, voir "Le serveur fait foi" ci-dessous.**
- **Le serveur fait foi** : revirement par rapport à la phase précédente — Firestore est désormais la source de vérité de la bibliothèque et des listes, AsyncStorage n'étant plus qu'une copie de secours hors-ligne. L'app affiche toujours la copie locale instantanément (rapide, marche hors ligne), puis la rafraîchit en arrière-plan depuis le serveur à deux moments seulement, jamais en continu : au démarrage (`App.tsx`) et à chaque ouverture/focus d'un écran de l'onglet "Ma bibliothèque" (`LibraryScreen` ET `ListDetailScreen`, via le hook partagé `useLibrarySync` — voir "Listes de lecture publiques" plus haut pour pourquoi ce mécanisme a été extrait dans un hook lors de la refonte "playlist" du 05/10/2026). Les nouveaux usecases `refreshLibraryFromServer`/`refreshListsFromServer` lisent Firestore (`fetchAll`, désormais utilisée pour ça en plus de la restauration d'un compte existant, voir plus bas) et **remplacent** la copie locale en cas de succès ; en cas d'échec (hors ligne, erreur), ils ne touchent à rien et laissent l'écran tel quel — best-effort et silencieux, comme le reste de la synchronisation cloud. La sauvegarde en masse (`syncLibraryToCloud`/`syncListsToCloud`) est désormais attendue avant ce rafraîchissement, à **chacun** des deux déclencheurs (pas seulement au démarrage), pour que le serveur ne réponde jamais avec une version en retard par rapport à des changements locaux pas encore remontés — **bug corrigé** : sans ce push également au focus de l'onglet, ajouter ou aimer un livre puis rouvrir/revenir sur "Ma bibliothèque" pouvait faire disparaître ce livre (la sauvegarde cloud de `addBook`/`toggleBookList` est en tâche de fond, jamais attendue, donc pas forcément déjà arrivée sur Firestore au moment du focus). **Deuxième bug corrigé, le push ci-dessus ne suffisait pas seul** : le livre pouvait encore disparaître si l'ajout/like (fait sur un autre écran) n'avait pas fini de mettre à jour Redux au moment où ce cycle push+pull démarrait, ou pendant l'aller-retour réseau du `fetchAll`. `librarySlice`/`listsSlice` ont donc chacun un compteur `revision`, incrémenté à chaque mutation locale ; `App.tsx`/`useLibrarySync` le lisent avant de pousser, et `refreshLibrary`/`refreshLists` jettent le résultat du serveur (sans toucher au local ni à Redux) si ce compteur a changé entre-temps — signe qu'une mutation locale plus récente existe et ne doit pas être écrasée par une réponse serveur désormais en retard par rapport à elle. **Troisième bug corrigé, pré-existant depuis la Phase 2 et resté invisible jusqu'ici** : `LibraryEntry.id`/`Book.id` (la clé "œuvre" Open Library, ex. `/works/OL136524W`, avec un `/` intégré) était utilisé tel quel comme id de document Firestore dans `FirestoreLibraryRepository`, ce que Firestore refuse (`/` est un séparateur de chemin) — `FirebaseError: Invalid document reference ... must have an even number of segments`. Comme `syncLibraryEntry` avale silencieusement toute erreur, aucun livre Open Library n'avait en réalité jamais été sauvegardé sur Firestore depuis la Phase 2 ; seuls les logs `[Readr][debug sync]` ajoutés pendant le travail sur les deux bugs ci-dessus l'ont enfin révélé. Fix : `FirestoreLibraryRepository` encode l'id en segment de chemin valide à l'écriture (`encodeURIComponent`) et le décode symétriquement à la lecture (`decodeURIComponent(d.id)` dans `fetchAll`) — l'id applicatif `LibraryEntry.id` ne change pas, seul l'id du document Firestore diffère de lui. Les listes de lecture ne sont pas concernées (leurs ids viennent de `generateId()`, un schéma déjà sûr pour Firestore).

"Policier", "Fantasy") sous chaque livre de Recherche et de Découvrir, déduits des sujets Open Library (`Book.genres`, `matchKnownGenres` dans `utils/genreLabels.ts`) ; aucun tag quand la source n'a pas de sujets ou qu'aucun genre connu ne correspond.
- **Profil façon Instagram (08/10/2026, demande explicite du porteur du projet : "Nom, Photo, description, compteur Suivis/Followers")** : `ProfileHeader` restructuré pour reprendre la mise en page d'un profil Instagram — avatar agrandi (56 → 76px) accompagné d'une rangée de deux compteurs (Abonnés/Abonnements), puis le pseudo, puis une nouvelle bio éditable. **Décision produit tranchée avec l'utilisateur, à ne pas perdre de vue : les compteurs Abonnés/Abonnements sont PUREMENT VISUELS, toujours à 0** — aucun système de followers n'a été construit (pas de collection Firestore, pas de bouton "suivre", pas d'écran de liste) ; l'option alternative (un vrai système de followers dès maintenant, une bonne partie de la Phase "Amis" en avance) a été explicitement écartée pour l'instant. La bio (`bio?: string` sur `users/{uid}`, même document que `username`/`photoUrl`) suit exactement la même mécanique que le pseudo (nouveau usecase `updateBio`, borné à 150 caractères comme Instagram), à une différence près : ses retours à la ligne sont conservés, contrairement au pseudo qui reste sur une seule ligne. Aucune nouvelle règle Firestore : `bio` vit dans le document déjà couvert par "Profil fusionné" ci-dessus.
- **Résultats de recherche regroupés par langue** : `SearchScreen` affiche les résultats en rows horizontales, une par langue (langue principale = `Book.languages[0]`, regroupement fait par `groupByLanguage` dans l'écran), dans l'ordre de première apparition — un tri par nombre de livres réordonnerait les rows à chaque page chargée. Le nom de la langue est cliquable et ouvre `LanguageResultsScreen`, qui ne se contente pas des livres déjà chargés dans la row : il relance une recherche dédiée filtrée côté serveur (`searchBooksInLanguage`, qui ajoute `language:<code>` à la requête Open Library), avec sa propre pagination, pour permettre de vraiment parcourir tous les livres de cette langue. Les labels de langue (`fre` → « Français », etc.) sont centralisés dans `src/utils/languageLabels.ts`, partagés avec la fiche livre.
- **Scanner** utilise `expo-camera` (`CameraView`) pour lire les codes-barres EAN-13 (format Bookland — numériquement l'ISBN-13 des livres, aucune conversion nécessaire). Le code scanné passe par `BookRepository.findByIsbn`, qui relance d'abord une recherche Open Library filtrée par ISBN (`isbn:<code>`) et réutilise le pipeline de regroupement existant. Une fois le livre trouvé, deux boutons ajoutent directement à la bibliothèque en statut « à lire » ou « lu » ; un lien permet aussi d'ouvrir la fiche complète. `expo-camera` a un vrai config plugin (contrairement à `expo-status-bar`/`expo-image`) : il doit rester dans `app.json` → `plugins`, avec le message de permission caméra.
  - **Repli catalogue pour les ISBN absents de l'index de recherche** : l'index de recherche d'Open Library (`search.json`) n'indexe pas toutes les éditions de son propre catalogue — en pratique, beaucoup d'éditions de poche françaises sont invisibles à la recherche alors qu'elles existent bien chez Open Library. Quand `isbn:<code>` ne renvoie rien, `findByIsbn` bascule sur `/isbn/<code>.json`, qui résout directement par clé dans le catalogue brut et a une bien meilleure couverture. Ce repli est plus coûteux (plusieurs appels : édition → œuvre → auteur(s), les noms d'auteur n'étant jamais donnés directement) et moins riche (pas d'année de première publication, pas de fusion multi-éditions), mais suffisant pour identifier et ajouter le livre scanné.
  - **Repli Google Books** : certaines éditions n'existent tout simplement pas chez Open Library, ni dans l'index de recherche ni dans le catalogue brut — constaté en pratique sur *Dracula* chez J'ai lu (ISBN 978-2-290-05740-7), un cas pourtant loin d'être exotique. Open Library reste un catalogue orienté fonds anglophones, avec une couverture inégale des éditions françaises grand public. Quand les deux étapes Open Library échouent, `findByIsbn` interroge l'API Google Books (`data/googleBooks/googleBooksClient.ts`), qui a une bonne couverture internationale et — contrairement à Open Library en échec ou à la BnF — renvoie une vraie couverture (`Book.coverUrl`, voir ci-dessus). Nécessite une clé API configurée dans `.env` (voir `.env.example` et la section Démarrer) : un premier essai anonyme avait été abandonné (429 systématique en test, quota en lecture seule quasi inexistant sans clé) ; avec une clé, l'appel est fiable. Sans clé configurée, ce repli est silencieusement sauté et `findByIsbn` passe directement à la BnF.
  - **Repli BnF en tout dernier recours** : si Google Books ne trouve rien non plus (ou si aucune clé n'est configurée), `findByIsbn` interroge l'API SRU de la Bibliothèque nationale de France (`data/bnf/bnfClient.ts`), qui couvre bien les livres publiés en France sans nécessiter de clé. Pas de JSON côté BnF : la réponse est du XML Dublin Core, extrait par expressions régulières (`data/bnf/xml.ts`) plutôt que d'ajouter une dépendance de parsing XML pour un usage aussi ciblé. Le livre trouvé est ajoutable normalement, mais sans couverture (la BnF n'expose pas d'image par cette API) et sans fiche détail enrichie (pas d'identifiant "œuvre" Open Library à interroger pour les éditions/langues — la fiche affiche juste "aucune édition référencée"). Si même la BnF échoue, le livre est vraiment introuvable par code-barres.

> ⚠️ **`app.json` → `plugins`** ne doit lister que des paquets qui exportent réellement un config plugin (vérifiable via `node_modules/<paquet>/package.json` → `main`/`exports` pointant vers `app.plugin.js`). En lister un qui n'en a pas fait planter `expo start` (voir l'historique du projet) — `expo-camera` en a un, `expo-status-bar` et `expo-image` n'en ont pas.
