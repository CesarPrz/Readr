# Readr

Appli mobile de recherche de livres (React Native + Expo) : recherche via l'API publique Open Library, fiche détail avec éditions/formats disponibles, et bibliothèque personnelle stockée localement sur l'appareil. Depuis les Phases 1 et 2 du plan Firebase (doc Claude du projet), une connexion Firebase anonyme et silencieuse tourne en tâche de fond dès le premier lancement, et la bibliothèque est sauvegardée vers Firestore au fil de l'eau (voir "Choix techniques" plus bas) — sans écran de compte ni rien à saisir, ce principe restant la règle pour toute future fonctionnalité sociale. Depuis la Phase 3, un onglet Profil permet de lier ce compte anonyme à Google — seul écran de l'app où une connexion est proposée, et seule partie du projet qui nécessite un dev client plutôt qu'Expo Go (voir "Phase 3 : connexion Google" plus bas).

> ⚠️ **Important, si tu reviens sur ce projet après une pause :** `app.json` liste maintenant `@react-native-google-signin/google-signin` dans `plugins` (Phase 3). Si ce paquet n'est pas encore installé, **`npm start`/`expo start` va planter** (Expo résout tous les plugins listés même en Expo Go, voir le paragraphe "Config plugins" du `CLAUDE.md` — déjà arrivé deux fois sur ce projet pour d'autres paquets). Lance `npx expo install @react-native-google-signin/google-signin` avant ton prochain `npm start`, que tu comptes travailler sur la Phase 3 tout de suite ou non.

## Démarrer

Depuis ce dossier, en local (Node ≥ 18) :

```bash
npm install
npx expo install --fix   # aligne les versions natives sur le SDK Expo installé
npx expo install expo-camera   # ajoute le scanner de code-barres (une fois, à la bonne version)
cp env.dev.example .env.dev   # puis remplis .env.dev (voir "Environnements" plus bas)
npm run start:dev             # active l'environnement dev et lance Expo
```

Scanne le QR code avec l'app **Expo Go** (iOS/Android) pour lancer l'appli sans build natif.

> **Clé API Google Books** : le repli `findByIsbn` du scanner (voir plus bas) utilise l'API Google Books, qui exige une clé même en lecture seule. Sans clé configurée, ce repli est silencieusement sauté (pas d'erreur) — le scanner reste fonctionnel, juste avec moins de couvertures pour les livres absents d'Open Library.

> **Config Firebase** : la connexion anonyme silencieuse (voir "Choix techniques") a besoin des six variables `EXPO_PUBLIC_FIREBASE_*` (config de l'app Web du projet Firebase, dans la Firebase Console) et de l'activation manuelle du fournisseur "Anonymous" (Authentication → Sign-in method). Sans ça, `ensureSignedIn` échoue silencieusement au démarrage — l'app reste par ailleurs pleinement utilisable, cette connexion ne bloque rien. Voir "Environnements (dev / prod)" ci-dessous pour la marche à suivre complète.

> Les fichiers ont été générés hors ligne (pas d'accès au registre npm depuis l'environnement qui les a écrits), donc les versions de dépendances dans `package.json` sont volontairement larges. `npx expo install --fix` corrige automatiquement toute incohérence de version avant le premier lancement.

## Environnements (dev / prod)

Deux projets Firebase séparés, pour ne jamais mélanger les données de test avec l'usage réel de l'app :

- **dev** — pour développer/tester : utilisateurs anonymes de test, données jetables.
- **prod** — pour ton usage réel de l'app : données à garder.

### Mettre en place le projet dev (si pas déjà fait)

1. `cp env.dev.example .env.dev`
2. Dans la [Firebase Console](https://console.firebase.google.com), ouvre ton projet Firebase existant → Paramètres du projet → Général → "Vos applications" → application Web (icône `</>`) — crée-en une si besoin (pas d'Hosting à activer) — copie les six valeurs dans `.env.dev`.
3. Authentication → Sign-in method → active le fournisseur **Anonymous**.
4. Firestore Database → **Créer une base de données** (mode production, la région n'a pas d'importance pour un usage perso) → onglet **Règles** → colle le contenu de `firestore.rules` (à la racine du dépôt) → Publier. Sans cette étape, la sauvegarde cloud de la bibliothèque (Phase 2) échoue silencieusement — l'app reste utilisable, juste sans sauvegarde.
5. `npm run env:dev` (ou directement `npm run start:dev`).

### Mettre en place le projet prod

1. Dans la Firebase Console → **Ajouter un projet** → un nouveau projet, distinct du projet dev (ex. renommer mentalement l'existant "readr-dev" et le nouveau "readr-prod" pour s'y retrouver).
2. Mêmes étapes que ci-dessus dans ce nouveau projet : application Web pour récupérer sa config, fournisseur Anonymous, **et** base Firestore + règles (`firestore.rules`) — les quatre étapes de la section dev, à refaire ici.
3. `cp env.prod.example .env.prod`, puis colle les valeurs de ce nouveau projet dedans.
4. `npm run env:prod` (ou `npm run start:prod`).

### Basculer entre les deux au quotidien

```bash
npm run env:dev     # ou : npm run start:dev  (bascule + lance Expo directement)
npm run env:prod    # ou : npm run start:prod
```

`npm run env:*` copie `.env.dev`/`.env.prod` vers `.env` — le seul fichier qu'Expo charge réellement. Ne remplis jamais `.env` à la main : il est régénéré à chaque bascule, toute modification directe serait écrasée. `EXPO_PUBLIC_APP_ENV` (présent dans les deux fichiers) s'affiche dans la console Metro/Expo Go au démarrage, avec l'identifiant du projet Firebase actif — un repère rapide pour vérifier qu'on n'est pas sur le mauvais projet avant de tester quoi que ce soit.

`.env.dev` et `.env.prod` ne sont jamais commités (voir `.gitignore`) ; `env.dev.example`/`env.prod.example` sont les templates versionnés. Voir aussi "Choix techniques" plus bas pour le détail (pourquoi un script maison plutôt que le mécanisme `NODE_ENV` intégré d'Expo).

## Phase 3 : connexion Google (nécessite un dev client)

**Pourquoi pas Expo Go ici, alors que tout le reste du projet l'utilise ?** Recherche documentée (sept. 2026) : la doc Expo actuelle exclut explicitement Expo Go pour tout flux OAuth ("Expo Go cannot be used for local development and testing of OAuth or OpenID Connect-enabled apps due to the inability to customize your app scheme"), et l'ancien contournement (`expo-auth-session/providers/google` + proxy `auth.expo.io`) a été entièrement retiré du SDK en 2023. Décision pour ce projet : la Phase 3 seule utilise un **dev client local** (`npx expo prebuild` + `npx expo run:android`/`run:ios`) — jamais le service cloud EAS Build. Tout le reste (Phases 1, 2, 4+, écrans existants) continue de tourner en Expo Go classique (`npm start`), sans rien à changer.

### Mise en place, par environnement (dev puis, plus tard, prod)

1. **Installer la lib** (une seule fois, avant même ton prochain `npm start` — voir l'avertissement en haut de ce README) :
   ```bash
   npx expo install @react-native-google-signin/google-signin
   ```
2. **Activer Google comme fournisseur** : Firebase Console (projet dev) → Authentication → Sign-in method → **Google** → activer. Juste en dessous, sous "Web SDK configuration", copie le **"Web client ID"** dans `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` de `.env.dev` (voir `env.dev.example`) — ce n'est pas le client Android ni iOS, malgré le nom.
3. **Télécharger les fichiers de config natifs**, toujours depuis ce même projet Firebase (Paramètres du projet → Général → tes apps Android/iOS — crée-les ici si elles n'existent pas encore, avec le `package`/`bundleIdentifier` de `app.json`, `com.cesar.readr`) :
   - `google-services.json` → renomme-le **`google-services.dev.json`**, à la racine du dépôt.
   - `GoogleService-Info.plist` → renomme-le **`GoogleService-Info.dev.plist`**, à la racine du dépôt.
   - Pour l'app **Android**, Firebase demande une empreinte SHA-1 : récupère-la avec `cd android && ./gradlew signingReport` (après un premier `npx expo prebuild`) et colle-la dans les paramètres de l'app Android sur Firebase Console — sans ça, `GoogleSignin.signIn()` échoue côté Android même avec le reste bien configuré.
4. **Activer l'environnement dev** (bascule maintenant aussi les fichiers Google, en plus de `.env`) :
   ```bash
   npm run env:dev
   ```
5. **Générer le projet natif et lancer le dev client** :
   ```bash
   npm run prebuild            # npx expo prebuild --clean — régénère android/ et ios/ à partir de app.json
   npm run devclient:android:dev   # ou : npm run devclient:ios:dev (nécessite un Mac)
   ```
   Ces deux commandes remplacent `expo start`/Expo Go **pour cette phase uniquement** — elles compilent et installent un vrai build de l'app (émulateur ou appareil connecté). Peut prendre plusieurs minutes la première fois (installation des dépendances natives Gradle/CocoaPods).
6. Une fois lancé, onglet **Profil** → "Se connecter avec Google". Vérifie ensuite, dans Firebase Console → Authentication → Users, que l'utilisateur anonyme existant a bien un e-mail Google associé (même `uid`, pas un nouvel utilisateur) — c'est le signe que la liaison (`linkWithCredential`, pas une nouvelle connexion) a fonctionné plutôt qu'une reconnexion depuis zéro.

**Pour le projet prod**, refaire les étapes 2 et 3 dans le second projet Firebase, en nommant les fichiers `google-services.prod.json` / `GoogleService-Info.prod.plist` / `.env.prod`, puis `npm run env:prod` + `npm run prebuild` + `npm run devclient:android:prod` (ou `:ios:prod`).

**Windows sans Mac** : `npx expo run:ios` n'est pas exécutable en local (nécessite Xcode). La configuration iOS (plugin, `GoogleService-Info.plist`) peut être préparée dès maintenant, mais son test réel attend un Mac (le tien, un service de build cloud type EAS Build si la contrainte "pas d'EAS Build" est reconsidérée un jour, ou une location ponctuelle) — l'Android peut avancer indépendamment en attendant.

**Après un changement d'environnement (`npm run env:dev`/`env:prod`)**, si tu utilises déjà le dev client, relance `npm run prebuild` avant de relancer `devclient:android:*`/`devclient:ios:*` : contrairement à `.env` (relu à chaque redémarrage Metro), `google-services.json`/`GoogleService-Info.plist` sont copiés dans le projet natif par `expo prebuild`, pas relus dynamiquement.

**Ce qui n'est pas géré à ce stade (voir le plan Firebase, doc Claude du projet)** : la fusion des bibliothèques si le compte Google est déjà lié à un autre utilisateur Firebase (`auth/credential-already-in-use`) — l'app affiche une erreur claire et n'essaie pas de fusionner ou de basculer automatiquement de compte.

## Structure (Clean Architecture + Redux)

- `src/domain/` — cœur métier, aucune dépendance à React Native, Redux ou Open Library
  - `entities/` — `Book`, `Edition`, `BookDetail` (dont `subjects`, les sujets Open Library bruts), `LibraryEntry`, `RecommendationGroup`, `UserProfile` (identité Firebase Auth courante)
  - `repositories/` — interfaces `BookRepository` / `LibraryRepository` / `AuthRepository` (dont `linkWithGoogle`/`signOutCurrentUser`, Phase 3) / `GoogleIdentityProvider` (Phase 3) / `LibrarySyncRepository` (ports)
  - `usecases/` — `searchBooks`, `searchBooksInLanguage`, `findBookByIsbn`, `getBookDetail`, `loadLibrary`, `addBookToLibrary`, `removeBookFromLibrary`, `updateLibraryEntry`, `getRecommendations`, `ensureSignedIn`, `syncLibraryEntry`, `removeLibraryEntryFromCloud`, `syncLibraryToCloud`, `linkGoogleAccount`, `signOutUser`
- `src/data/` — implémentations concrètes des ports du domain
  - `openLibrary/` — `OpenLibraryBookRepository` (appels HTTP + mapping vers les entités du domain)
  - `googleBooks/` — repli de `findByIsbn` (clé API requise, voir "Environnements" plus haut), utilisé quand Open Library (index + catalogue) ne trouve rien ; seule source de repli à fournir une couverture (`Book.coverUrl`)
  - `bnf/` — dernier recours de `findByIsbn`, après Google Books (pas de repository à part entière, juste un client + mapping utilisés en interne par `OpenLibraryBookRepository`)
  - `local/` — `AsyncStorageLibraryRepository` (bibliothèque locale persistée)
  - `firebase/` — `FirebaseAuthRepository` (connexion anonyme, liaison Google, déconnexion) + `FirestoreLibraryRepository` (sauvegarde cloud de la bibliothèque) — SDK JS modulaire Firebase, voir "Choix techniques"
  - `google/` — `GoogleSignInProvider` (Phase 3, lib native — seul module qui ne tourne pas dans Expo Go, voir "Phase 3 : connexion Google")
- `src/composition/repositories.ts` — seul fichier qui instancie les implémentations concrètes ; tout le reste dépend des interfaces du domain
- `src/store/` — state management Redux Toolkit : `librarySlice`, `searchSlice`, `languageResultsSlice`, `bookDetailSlice`, `discoverSlice`, `scanSlice`, `authSlice` (thunks qui appellent les usecases, dont `linkGoogleAccount`/`signOutUser`), `store.ts`, `hooks.ts` (`useAppDispatch`/`useAppSelector`)
- `src/theme/` — couleurs, espacements, typographie (thème sombre inspiré de la référence UI)
- `src/utils/` — helpers de présentation partagés entre écrans, sans dépendance à Redux/API (`languageLabels.ts`, `anonymousPseudonym.ts` — pseudonyme cosmétique du profil anonyme, Phase 3)
- `src/navigation/` — barre d'onglets (Recherche / Scanner / Découvrir / Ma bibliothèque / Profil) + piles de navigation
- `src/screens/` — Recherche, Résultats par langue, Scanner, Découvrir, Fiche livre, Ma bibliothèque, Profil (Phase 3 — branchées sur le store Redux, plus d'appel direct à l'API ou à AsyncStorage)
- `src/components/` — carte livre, badge de format, étoiles de notation, sélecteur de statut, carrousel de couvertures (purement présentationnels)

Sens de dépendance : `screens/` et `store/` → `domain/` (interfaces) ; `data/` → implémente `domain/` ; `composition/` relie les deux. Aucun écran n'importe `data/` directement.

`src/api/` et `src/storage/` (l'ancienne implémentation Context + appels directs) sont obsolètes et vidés de leur contenu — à supprimer manuellement, rien ne les importe plus.

## Choix techniques (vs. le cahier des charges initial)

- **Redux Toolkit** pour le state partagé (bibliothèque, recherche, détail livre) organisé en **Clean Architecture** (domain / data / composition), à la demande explicite du porteur du projet — remplace le Context + AsyncStorage fait maison de la première version.
- **FlatList** plutôt que FlashList : moins de dépendances tierces à faire correspondre à la main sans pouvoir tester l'installation depuis l'environnement de génération initial. Fonctionnellement équivalent pour ce volume de données ; migrable plus tard si besoin de perf sur de très longues listes.
- Aucune donnée d'audiobook commercial (type Audible) n'existe en accès public : l'appli affiche un badge « disponible en édition audio » uniquement quand Open Library référence un format audio, sans lecteur ni lien d'achat.
- **Découvrir** affiche plusieurs rows de recommandations, chacune avec sa propre justification plutôt qu'une seule liste mélangée (`getRecommendations`, qui renvoie des `RecommendationGroup[]` — voir `domain/entities/RecommendationGroup.ts`) : jusqu'à 2 rows "Car vous avez lu X (et Y)" (par auteur, à partir des livres au statut "lu"), jusqu'à 2 rows "Car vous avez aimé X (et Y)" (par auteur, à partir des livres `liked` — voir la liste "Aimé" de la bibliothèque), et au plus une row "D'autres classiques du genre <sujet>" basée sur les sujets Open Library (`BookDetail.subjects`) du livre lu ou aimé le plus récent. Un même auteur n'est jamais recommandé pour deux raisons différentes — "lu" est prioritaire sur "aimé". Chaque row relance une recherche Open Library (par auteur, ou `subject:"<sujet>"` pour la row de genre) et exclut les livres déjà dans la bibliothèque ; une row sans aucun nouveau résultat n'est simplement pas affichée. Recalculé à chaque ajout/retrait dans la bibliothèque.
  - **Genre approximatif** : les sujets Open Library sont une liste libre (mélange de genres, thèmes, prix littéraires...), pas une taxonomie de genres propre, et souvent en anglais même pour un livre francophone — `subjects[0]` est utilisé tel quel comme libellé de genre, sans traduction ni nettoyage. Heuristique faible, mais pas d'autre source de genre disponible sans API supplémentaire.
- **Regroupement des doublons de recherche** : Open Library indexe souvent le même livre sous plusieurs fiches "work" distinctes (doublons de catalogage, traductions non reliées à l'œuvre d'origine), ce qui faisait apparaître un même livre plusieurs fois dans les résultats. `docsToBooks` (dans `data/openLibrary/mappers.ts`) regroupe les résultats d'une page par titre + premier auteur normalisés, fusionne leurs identifiants d'œuvre et leurs langues, et la fiche détail agrège ensuite éditions/langues de tous les identifiants fusionnés (`BookRepository.getDetail` prend un tableau d'identifiants). Heuristique, pas une garantie : le regroupement ne se fait qu'au sein d'une page de résultats, jamais entre plusieurs pages, et deux livres différents partageant exactement un titre et un premier auteur seraient (rarement) fusionnés à tort.
  - **Choix de la couverture** : pour un groupe fusionné, `pickCoverId` retient la couverture de la fiche dont `first_publish_year` est le plus récent, plutôt que la première couverture rencontrée. Motivation : pour les classiques du domaine public, la couverture "par défaut" que renvoie Open Library est très souvent celle de la toute première édition numérisée, qui ne ressemble à aucune édition courante. Heuristique faible et non garantie — `first_publish_year` reste un champ par fiche "œuvre" de l'index de recherche, pas l'année précise de l'édition d'où vient la couverture — mais un biais vers le plus récent du groupe est préférable à un choix arbitraire, sans appel réseau supplémentaire. Les couvertures elles-mêmes restent celles qu'Open Library a scannées : pour beaucoup de classiques, aucune édition récente n'a de couverture référencée du tout, auquel cas ce choix ne change rien.
- **Liste "Aimé" et bulle cœur** : `LibraryEntry.liked?: boolean` est indépendant du statut de lecture (`ReadingStatus`) — un livre "à lire" peut très bien être aimé. `LibraryScreen` a donc un 4ᵉ onglet "Aimé" (à côté de À lire / En cours / Lu) qui filtre sur ce champ plutôt que sur `status`. Sur la fiche livre, une bulle en forme de cœur (coin haut-droit de la couverture) bascule ce champ ; si le livre n'est pas encore dans la bibliothèque, appuyer dessus l'y ajoute directement (statut "à lire" par défaut) plutôt que d'obliger à d'abord passer par "Ajouter à ma bibliothèque" — "Aimé" reste une des listes de la bibliothèque, un livre non ajouté ne peut pas y figurer.
- **Ordre de la fiche livre** : le résumé est affiché juste après le titre/auteur (et le badge audio éventuel), avant le bouton d'ajout et les contrôles de statut/note/notes personnelles — pour permettre de se décider à la lecture du résumé avant de choisir une liste. Les éditeurs et langues disponibles restent en bas de fiche.
- **Éditeurs plutôt que formats sur la fiche livre** : la section "Éditions disponibles" (badges de format par édition) a été remplacée par "Éditeurs" — une liste des éditeurs connus (`Edition.publisher`, tiré de `publishers[0]` côté Open Library), dédupliqués et affichés en texte simple, comme la liste des langues. Beaucoup d'éditions n'ont pas d'éditeur renseigné : dans ce cas, un texte de repli s'affiche ("Aucun éditeur référencé pour ce livre.") plutôt que rien du tout. Le résumé a le même traitement : quand Open Library n'a pas de description pour l'œuvre (fréquent pour certains titres, ex. *Les Thanatonautes* de Bernard Werber), un texte de repli s'affiche plutôt que de faire disparaître silencieusement toute la section "Résumé".
- **Couvertures multiples sur la fiche livre** : les éditions fusionnées d'un même livre (voir regroupement des doublons ci-dessous) peuvent chacune référencer une couverture différente — `Edition.coverId` porte désormais cette info (`data/openLibrary/mappers.ts`). `BookDetailScreen` construit la liste des couvertures connues (`presetCoverUrl` en premier s'il existe, puis `presetCoverId`, puis celles des éditions chargées, dédupliquées) et les passe à `CoverCarousel`, qui affiche une image statique s'il n'y en a qu'une, ou un carrousel swipable avec indicateurs à points sinon. Composant purement présentationnel : reçoit des URLs déjà résolues, jamais de `coverId` ni d'appel à `bookRepository`.
- **Deux représentations de couverture sur `Book`/`LibraryEntry`** : `coverId?: number` suit le schéma numérique d'Open Library (résolu en URL via `bookRepository.coverUrl(id, taille)`) ; `coverUrl?: string` porte une URL déjà résolue, pour les sources qui n'ont pas d'identifiant Open Library (ex. Google Books). Partout où une couverture est affichée, la règle est `book.coverUrl ?? bookRepository.coverUrl(book.coverId, taille)` — `coverUrl` est prioritaire quand il existe.
- **Résumé de repli venu de Google Books** : `getDetail`/`fetchBookDetail` n'enrichissent un livre qu'à partir d'une vraie fiche "œuvre" Open Library — pour un livre trouvé via le repli Google Books (`data/googleBooks/`, pas de fiche "œuvre" associée), ce résumé Open Library n'arrivera jamais. `Book.description` porte donc, comme `coverUrl`, un résumé déjà connu au moment où le livre est trouvé (le champ `description` du volume Google Books). `BookDetailScreen` garde le résumé Open Library prioritaire quand il existe (généralement plus complet/à jour), et ne retombe sur `presetDescription` que s'il n'y en a pas — sinon un livre venu de Google Books n'aurait jamais de résumé du tout, même quand Google Books en avait un.
  - **Et pour les livres bien référencés sur Open Library mais sans résumé ?** Cas distinct du précédent : l'œuvre existe bien chez Open Library (éditions, couvertures...) mais son champ `description` est simplement vide — constaté en pratique sur *Les Thanatonautes* de Bernard Werber, malgré 4 éditions connues. `OpenLibraryBookRepository.getDetail` retente alors Google Books, cette fois par titre + premier auteur (`findDescriptionOnGoogleBooks`, dans `data/googleBooks/googleBooksClient.ts`) puisqu'on n'a pas d'ISBN à ce stade — seulement les métadonnées de la fiche "œuvre" déjà chargée. Recherche par titre/auteur, meilleure correspondance seulement : moins fiable qu'une recherche par ISBN, mais suffisant pour un résumé (contrairement à une couverture ou une édition, un résumé légèrement décalé entre éditions reste presque toujours correct). Nécessite la même clé API que les autres replis Google Books ; sans clé, sauté silencieusement.
- **Connexion Firebase anonyme et silencieuse (Phase 1 du plan Firebase)** : `ensureSignedIn` (dispatché une fois au démarrage dans `App.tsx`) crée une identité Firebase Auth anonyme au tout premier lancement, sans le moindre écran — fondation pour la sauvegarde cloud et les fonctionnalités sociales à venir (voir le plan, doc Claude du projet), pas encore branchée à quoi que ce soit de visible. SDK JS modulaire (`firebase`, pas `@react-native-firebase`) pour rester compatible Expo Go, avec persistance de session via `initializeAuth` + `getReactNativePersistence(AsyncStorage)` (sans quoi la session ne survivrait pas à un redémarrage de l'app). `FirebaseAuthRepository` attend le premier `onAuthStateChanged` avant de décider de créer un nouvel utilisateur anonyme, pour ne pas en recréer un (et perdre le précédent) à chaque démarrage pendant que la session persistée se restaure de façon asynchrone. Principe directeur pour toute la suite : jamais de demande de connexion pour une fonctionnalité de base, une invite n'apparaît qu'au moment précis où une fonctionnalité sociale en a réellement besoin.
- **Deux projets Firebase (dev / prod), basculés par script maison** : voir "Environnements (dev / prod)" plus haut pour la marche à suivre. Techniquement, `scripts/use-env.js` copie `.env.dev` ou `.env.prod` vers `.env` (le seul fichier qu'Expo charge). Pas de `.env.development`/`.env.production` + `NODE_ENV` (le mécanisme intégré d'Expo) : ce mécanisme ne s'active que pour `expo export`/EAS Build, jamais pour `expo start` (seul mode utilisé ici, Expo Go sans build) — le déclencher manuellement pour `expo start` est explicitement déconseillé par la doc Expo elle-même (effets de bord sur d'autres outils lisant `NODE_ENV`), qui recommande justement un script de copie pour ce cas. `EXPO_PUBLIC_APP_ENV` (loggé au démarrage avec le `projectId` actif, voir `data/firebase/firebaseApp.ts`) est un simple repère de vérification, pas un flag qui change le comportement de l'app.
- **Sauvegarde cloud de la bibliothèque (Phase 2 du plan Firebase)** : chaque ajout/changement de statut/note/aimé/suppression sur la bibliothèque est répliqué vers Firestore (`users/{uid}/library/{bookId}`) juste après l'écriture locale, en tâche de fond et sans jamais bloquer l'UI (`librarySlice` appelle le usecase de sync sans l'attendre) — un passage `syncLibraryToCloud` au démarrage couvre aussi les entrées ajoutées avant l'existence de cette phase. À sens unique et best-effort : le local (AsyncStorage) reste l'unique source de vérité, rien ne restaure encore depuis le cloud, et toute erreur (hors ligne, base Firestore pas encore créée côté console) est avalée silencieusement plutôt que remontée à l'utilisateur. Seuls `title`/`authors`/`coverId`/`coverUrl`/`status`/`liked`/`rating`/`updatedAt` sont synchronisés — jamais `note` (carnet personnel, reste local). Nécessite `initializeFirestore(app, { experimentalAutoDetectLongPolling: true })` plutôt que `getFirestore` seul (le transport de streaming par défaut de Firestore est peu fiable sur React Native), et une base Firestore + les règles de `firestore.rules` créées manuellement dans chaque projet (voir "Environnements" plus haut) — sans ça, la sauvegarde échoue silencieusement, sans affecter le reste de l'app.
- **Liaison Google Sign-In (Phase 3 du plan Firebase), et pourquoi elle sort du cadre Expo Go** : voir la section dédiée "Phase 3 : connexion Google" plus haut pour la marche à suivre complète. En résumé, techniquement : deux ports domain séparés (`GoogleIdentityProvider`, qui ne parle qu'à Google, et `AuthRepository.linkWithGoogle`, qui ne parle qu'à Firebase) plutôt qu'un seul mélangeant les deux — si la lib Google Sign-In change un jour, seul `data/google/GoogleSignInProvider.ts` est concerné. `linkWithCredential` (pas une nouvelle connexion) préserve l'`uid` existant, donc la bibliothèque cloud déjà sauvegardée (Phase 2) reste associée à l'utilisateur une fois lié. Le cas où ce compte Google est déjà lié à un *autre* utilisateur Firebase (`auth/credential-already-in-use` — app réinstallée, ou compte déjà utilisé sur un autre appareil) est détecté et affiché clairement à l'utilisateur, sans tentative de fusion des bibliothèques ni de bascule automatique de compte (non implémenté, voir le plan). Écran Profil volontairement isolé dans son propre onglet plutôt qu'une bannière globale, conformément au principe de connexion non intrusive.
- **Résultats de recherche regroupés par langue** : `SearchScreen` affiche les résultats en rows horizontales, une par langue (langue principale = `Book.languages[0]`, regroupement fait par `groupByLanguage` dans l'écran), dans l'ordre de première apparition — un tri par nombre de livres réordonnerait les rows à chaque page chargée. Le nom de la langue est cliquable et ouvre `LanguageResultsScreen`, qui ne se contente pas des livres déjà chargés dans la row : il relance une recherche dédiée filtrée côté serveur (`searchBooksInLanguage`, qui ajoute `language:<code>` à la requête Open Library), avec sa propre pagination, pour permettre de vraiment parcourir tous les livres de cette langue. Les labels de langue (`fre` → « Français », etc.) sont centralisés dans `src/utils/languageLabels.ts`, partagés avec la fiche livre.
- **Scanner** utilise `expo-camera` (`CameraView`) pour lire les codes-barres EAN-13 (format Bookland — numériquement l'ISBN-13 des livres, aucune conversion nécessaire). Le code scanné passe par `BookRepository.findByIsbn`, qui relance d'abord une recherche Open Library filtrée par ISBN (`isbn:<code>`) et réutilise le pipeline de regroupement existant. Une fois le livre trouvé, deux boutons ajoutent directement à la bibliothèque en statut « à lire » ou « lu » ; un lien permet aussi d'ouvrir la fiche complète. `expo-camera` a un vrai config plugin (contrairement à `expo-status-bar`/`expo-image`) : il doit rester dans `app.json` → `plugins`, avec le message de permission caméra.
  - **Repli catalogue pour les ISBN absents de l'index de recherche** : l'index de recherche d'Open Library (`search.json`) n'indexe pas toutes les éditions de son propre catalogue — en pratique, beaucoup d'éditions de poche françaises sont invisibles à la recherche alors qu'elles existent bien chez Open Library. Quand `isbn:<code>` ne renvoie rien, `findByIsbn` bascule sur `/isbn/<code>.json`, qui résout directement par clé dans le catalogue brut et a une bien meilleure couverture. Ce repli est plus coûteux (plusieurs appels : édition → œuvre → auteur(s), les noms d'auteur n'étant jamais donnés directement) et moins riche (pas d'année de première publication, pas de fusion multi-éditions), mais suffisant pour identifier et ajouter le livre scanné.
  - **Repli Google Books** : certaines éditions n'existent tout simplement pas chez Open Library, ni dans l'index de recherche ni dans le catalogue brut — constaté en pratique sur *Dracula* chez J'ai lu (ISBN 978-2-290-05740-7), un cas pourtant loin d'être exotique. Open Library reste un catalogue orienté fonds anglophones, avec une couverture inégale des éditions françaises grand public. Quand les deux étapes Open Library échouent, `findByIsbn` interroge l'API Google Books (`data/googleBooks/googleBooksClient.ts`), qui a une bonne couverture internationale et — contrairement à Open Library en échec ou à la BnF — renvoie une vraie couverture (`Book.coverUrl`, voir ci-dessus). Nécessite une clé API configurée dans `.env` (voir `.env.example` et la section Démarrer) : un premier essai anonyme avait été abandonné (429 systématique en test, quota en lecture seule quasi inexistant sans clé) ; avec une clé, l'appel est fiable. Sans clé configurée, ce repli est silencieusement sauté et `findByIsbn` passe directement à la BnF.
  - **Repli BnF en tout dernier recours** : si Google Books ne trouve rien non plus (ou si aucune clé n'est configurée), `findByIsbn` interroge l'API SRU de la Bibliothèque nationale de France (`data/bnf/bnfClient.ts`), qui couvre bien les livres publiés en France sans nécessiter de clé. Pas de JSON côté BnF : la réponse est du XML Dublin Core, extrait par expressions régulières (`data/bnf/xml.ts`) plutôt que d'ajouter une dépendance de parsing XML pour un usage aussi ciblé. Le livre trouvé est ajoutable normalement, mais sans couverture (la BnF n'expose pas d'image par cette API) et sans fiche détail enrichie (pas d'identifiant "œuvre" Open Library à interroger pour les éditions/langues — la fiche affiche juste "aucune édition référencée"). Si même la BnF échoue, le livre est vraiment introuvable par code-barres.

> ⚠️ **`app.json` → `plugins`** ne doit lister que des paquets qui exportent réellement un config plugin (vérifiable via `node_modules/<paquet>/package.json` → `main`/`exports` pointant vers `app.plugin.js`). En lister un qui n'en a pas fait planter `expo start` (voir l'historique du projet) — `expo-camera` en a un, `expo-status-bar` et `expo-image` n'en ont pas.
