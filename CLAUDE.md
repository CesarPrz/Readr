# Readr — directives pour Claude

Appli mobile de recherche de livres (React Native + Expo). Recherche via Open Library, fiche détail avec éditions/formats, bibliothèque personnelle en local. Voir le cahier des charges (doc Claude du projet) pour la vision produit et la roadmap ; ce fichier ne couvre que les règles techniques du code.

Depuis les Phases 1 et 2 du plan Firebase (doc Claude du projet, "firebase-social-plan"), l'app a une connexion Firebase anonyme et silencieuse en tâche de fond et sauvegarde la bibliothèque vers Firestore (voir sections dédiées plus bas). Depuis la Phase 3, un onglet Profil permet de lier ce compte anonyme à Google, à l'initiative explicite de l'utilisateur — le principe de connexion non intrusive reste entier pour tout le reste de l'app : rien à saisir, rien à voir, sauf sur cet unique écran qu'on va chercher soi-même. Depuis la section "Listes de lecture publiques" (voir plus bas), les 4 listes historiques (À lire/En cours/Lu/Aimés) et les listes perso de l'utilisateur sont des `ReadingList` génériques, stockées localement (hors-ligne) et en Firestore en LECTURE PUBLIQUE — n'importe quel utilisateur peut voir la bibliothèque et les listes de n'importe qui (pas encore de navigation UI pour ça, voir la section dédiée). **Depuis la section "Firebase (Le serveur fait foi)" (voir plus bas), Firestore est devenu la source de vérité de la bibliothèque/des listes — revirement par rapport aux Phases 1/2 où le local seul faisait foi ; AsyncStorage n'est plus qu'une copie de secours hors-ligne, rafraîchie depuis le serveur au démarrage et à l'ouverture de l'onglet Bibliothèque.**

**Exception importante au workflow habituel, introduite par la Phase 3 :** ce projet visait initialement à rester 100 % Expo Go (aucun dev client, aucun EAS Build) — voir le cahier des charges et le plan Firebase pour l'historique de cette contrainte. Une recherche documentée (Sept. 2026) a confirmé qu'aucune lib de connexion Google (native ou via `expo-auth-session`, dont le proxy `auth.expo.io` a été entièrement retiré du SDK en 2023) ne fonctionne dans Expo Go — la doc Expo elle-même l'exclut explicitement pour tout flux OAuth. Décision assumée avec l'utilisateur : la Phase 3 seule sort du cadre Expo Go et utilise un **dev client local** (`npx expo run:android` / `run:ios`, généré par `npx expo prebuild` — pas de service cloud EAS Build). Tout le reste du projet (Phases 1, 2, 4+, et le développement quotidien des écrans existants) continue de tourner en Expo Go classique (`npm start`) sans aucun changement. Voir la section "Firebase (Phase 3 : connexion Google)" plus bas pour le détail.

## Architecture : Clean Architecture + Redux

Le code est organisé en couches, avec une règle de dépendance stricte : **le domain ne dépend de rien, tout le reste dépend du domain.**

```
domain/   (règles métier pures)
  ↑
data/     (implémente les interfaces du domain)
  ↑
composition/  (assemble domain + data)
  ↑
store/, screens/, components/  (consomment le domain via composition)
```

- `src/domain/` — cœur métier. Aucun import de React, React Native, Redux, Open Library ou AsyncStorage.
  - `entities/` — types métier purs : `Book`, `Edition` (dont `coverId?`, une édition peut avoir sa propre couverture ; `publisher?`, pas toujours renseigné), `BookDetail` (dont `subjects: string[]`, les sujets Open Library bruts — utilisés par `getRecommendations` pour la row de genre, jamais affichés tels quels : `utils/genreLabels.ts` (`matchKnownGenre`, 07/10/2026) les compare à une liste fermée de genres usuels — Horreur, Policier, Romance, Fantasy, Biographie... — avant d'en afficher un, voir le README pour le détail et l'historique), `LibraryEntry` (dont `listIds: string[]` — les `ReadingList` auxquelles ce livre appartient, voir `ReadingList.ts` ; remplace les anciens `status`/`liked`), `ReadingList` (une liste de lecture — les 4 listes historiques et les listes perso de l'utilisateur, voir section "Listes de lecture publiques" plus bas), `RecommendationGroup` (une row de "Découvrir" : `title` + `books`, voir `getRecommendations`), `UserProfile` (dont `isAnonymous: boolean` — identité Firebase Auth courante, voir section Firebase plus bas). `Book` et `LibraryEntry` portent deux champs de couverture : `coverId?: number` (schéma Open Library, résolu via `bookRepository.coverUrl(id, taille)`) et `coverUrl?: string` (URL déjà résolue, pour les sources sans identifiant Open Library, ex. `data/googleBooks/`). Partout où une couverture est affichée : `book.coverUrl ?? bookRepository.coverUrl(book.coverId, taille)`. Même logique pour `description?: string` : un résumé déjà connu pour les sources sans fiche "œuvre" Open Library à interroger — `BookDetailScreen` garde le résumé Open Library (`BookDetail.description`, une fois chargé) prioritaire, `Book.description`/`presetDescription` ne sert que de repli.
  - `repositories/` — interfaces (ports) : `BookRepository`, `LibraryRepository`, `ListRepository` (local, listes de lecture — même forme que `LibraryRepository`), `AuthRepository` (session utilisateur — voir section Firebase plus bas ; `ensureSignedIn`/`getCurrentUser` depuis la Phase 1, `linkWithGoogle`/`signOutCurrentUser` depuis la Phase 3 — `linkWithGoogle` renvoie un `LinkGoogleOutcome` avec `switchedToExistingAccount`, voir "Bascule vers un compte existant"), `GoogleIdentityProvider` (Phase 3 — flux natif de connexion Google, obtention d'un ID token ; ne connaît que Google, jamais Firebase, c'est `AuthRepository.linkWithGoogle` qui fait le pont), `LibrarySyncRepository` (sauvegarde cloud de la bibliothèque, Phase 2 — voir section Firebase plus bas ; `upsertEntry`/`removeEntry` best-effort à sens unique, plus `fetchAll` — lecture utilisée à la fois pour la restauration d'un compte existant et pour le rafraîchissement régulier "le serveur fait foi", voir section dédiée), `ListSyncRepository` (pendant pour les listes — voir section "Listes de lecture publiques", même `fetchAll`). Elles décrivent un contrat, jamais une implémentation.
  - `usecases/` — une fonction par action métier (`searchBooks`, `searchBooksInLanguage`, `findBookByIsbn`, `addBookToLibrary`, `updateLibraryEntry`, `toggleBookList`, `getRecommendations`, `ensureSignedIn`, `syncLibraryEntry`, `removeLibraryEntryFromCloud`, `syncLibraryToCloud`, `linkGoogleAccount`, `signOutUser`, `seedDefaultLists`, `createReadingList`, `renameReadingList`, `deleteReadingList`, `syncListEntry`, `syncListsToCloud`, `removeListFromCloud`...). Prennent un repository en premier paramètre (injection par argument, pas de DI framework) — `deleteReadingList` en prend deux (`ListRepository` + `LibraryRepository`, pour retirer une liste supprimée des `listIds` des livres concernés en une seule opération), et `linkGoogleAccount` cinq (`GoogleIdentityProvider` + `AuthRepository` + `LibraryRepository` + `ListRepository` + `LibrarySyncRepository` + `ListSyncRepository` — voir "Bascule vers un compte existant" pour pourquoi), pour orchestrer plusieurs ports sans que ni le thunk ni un troisième composant n'ait à le faire. `getRecommendations` renvoie plusieurs `RecommendationGroup[]` (pas un `Book[]` plat) : la logique de regroupement par auteur/raison et la recherche du genre vivent entièrement dans le usecase, `discoverSlice`/`DiscoverScreen` ne font qu'afficher les groupes reçus. `syncLibraryEntry`/`removeLibraryEntryFromCloud`/`syncLibraryToCloud`/`syncListEntry`/`syncListsToCloud`/`removeListFromCloud` sont volontairement best-effort (erreurs avalées, voir section Firebase) — même esprit que `searchExcluding` dans `getRecommendations`.
- `src/data/` — implémentations concrètes des interfaces du domain.
  - `openLibrary/` — `OpenLibraryBookRepository` (appels HTTP, dont `findByIsbn` pour le scanner) + `mappers.ts` (JSON brut → entités du domain, avec le regroupement des doublons) + `types.ts` (formats bruts de l'API, jamais exposés hors de ce dossier).
  - `googleBooks/` — deux replis distincts vers l'API Google Books, appelés en interne par `OpenLibraryBookRepository`, tous deux silencieusement sautés sans clé API (`EXPO_PUBLIC_GOOGLE_BOOKS_API_KEY`, voir section Environnements ci-dessous) : `findByIsbnOnGoogleBooks` (repli de `findByIsbn` par ISBN, quand Open Library index + catalogue ne trouvent rien, avant la BnF — seule source à fournir une vraie couverture, `Book.coverUrl`) et `findDescriptionOnGoogleBooks` (repli de `getDetail` par titre + auteur, quand la fiche "œuvre" Open Library existe mais n'a pas de `description`). Pas un `BookRepository` à part entière : `googleBooksClient.ts` + `mappers.ts` + `types.ts`, même séparation raw-types/mapping que les autres sources.
  - `bnf/` — tout dernier repli de `findByIsbn` (API SRU de la Bibliothèque nationale de France), appelé en interne par `OpenLibraryBookRepository` quand ni Open Library (index + catalogue) ni Google Books ne trouvent rien pour un ISBN. Pas un `BookRepository` à part entière (pas de `search`/`getDetail`) : juste `bnfClient.ts` + `xml.ts` (extraction du XML Dublin Core par regex, pas de JSON côté BnF) + `mappers.ts` + `types.ts`, même séparation raw-types/mapping que les autres sources. N'expose pas de couverture.
  - `local/` — `AsyncStorageLibraryRepository` (migre silencieusement les anciennes entrées `status`/`liked` vers `listIds` à la lecture, voir sa doc) + `AsyncStorageListRepository`.
  - `firebase/` — `FirebaseAuthRepository` (implémente `AuthRepository`) + `FirestoreLibraryRepository` (implémente `LibrarySyncRepository`, Phase 2) + `FirestoreListRepository` (implémente `ListSyncRepository`, listes de lecture publiques) + `firebaseApp.ts` (init de l'app Firebase, de l'instance Auth et de l'instance Firestore) + `mappers.ts` (`firebase/auth`'s `User` → `UserProfile`, `LibraryEntry` → document Firestore, `ReadingList` → document Firestore), même séparation raw-types/mapping que les autres sources. Voir section Firebase dédiée plus bas pour le détail technique (persistance, connexion anonyme, sauvegarde cloud).
  - `google/` — `GoogleSignInProvider` (implémente `GoogleIdentityProvider`, Phase 3) via la lib native `@react-native-google-signin/google-signin`. Seul module de `data/` qui ne peut pas tourner dans Expo Go (voir section Firebase Phase 3 plus bas).
- `src/composition/repositories.ts` — **seul fichier autorisé à importer une classe concrète de `data/`**. Instancie `bookRepository`, `libraryRepository`, `listRepository`, `authRepository`, `librarySyncRepository`, `listSyncRepository` et `googleIdentityProvider`, exportés typés en interfaces du domain.
- `src/store/` — Redux Toolkit. Un slice par domaine fonctionnel (`librarySlice`, `listsSlice`, `searchSlice`, `languageResultsSlice`, `bookDetailSlice`, `discoverSlice`, `scanSlice`, `authSlice`). Les thunks appellent des usecases avec les repositories importés depuis `composition/`, jamais depuis `data/` directement. `authSlice.ensureSignedIn` est dispatché une seule fois, silencieusement, au démarrage de l'app (`App.tsx`) — jamais en réaction à une action de l'utilisateur. `librarySlice.addBook`/`removeBook`/`patchLibraryEntry`/`toggleBookList` et `listsSlice.createList`/`renameList`/`deleteList` déclenchent aussi, en tâche de fond sans l'attendre (`void`, jamais `await`), la sauvegarde cloud correspondante (Phase 2/"Listes de lecture publiques") — voir l'exception à la règle 7 ci-dessous. `librarySlice.syncLibraryToCloud`/`listsSlice.syncListsToCloud` (sauvegarde en masse) sont dispatchés une seule fois au démarrage, depuis `App.tsx`, après `fetchLibrary`/`fetchLists` et `ensureSignedIn`, et **attendus** (contrairement à la sauvegarde au fil de l'eau) avant de rafraîchir depuis le serveur — voir section "Firebase (Le serveur fait foi)". `librarySlice.refreshLibrary`/`listsSlice.refreshLists` relisent Firestore et écrasent le cache local (`entries`/`lists` inchangés si le serveur ne répond pas) : dispatchés depuis `App.tsx` juste après cette sauvegarde en masse, et depuis `LibraryScreen` à chaque focus de l'onglet (`useFocusEffect`). `listsSlice.deleteList` dispatche aussi une action simple (`librarySlice.setLibraryEntries`) pour répercuter dans `library` le retrait de la liste supprimée des `listIds` concernés — une synchronisation d'état entre deux slices pour un seul geste utilisateur, pas un second usecase. `authSlice.linkGoogleAccount`/`signOutUser` (Phase 3) ne sont dispatchés que depuis `ProfilScreen`, jamais automatiquement ; `linkGoogleAccount` dispatche lui aussi `setLibraryEntries`/`listsSlice.setLists` quand son résultat est `switched` (voir "Bascule vers un compte existant"), même pattern que `deleteList`.
- `src/screens/`, `src/components/`, `src/navigation/`, `src/theme/` — présentation. Consomment le store via `useAppDispatch`/`useAppSelector` (`src/store/hooks.ts`). Cinq onglets : Recherche, Scanner, Découvrir, Ma bibliothèque, Profil (Phase 3 — voir section Firebase dédiée).
- `src/utils/` — helpers de présentation partagés entre écrans (ex. `languageLabels.ts`, `anonymousPseudonym.ts`), sans dépendance à Redux/API. Différent de `domain/` : ce ne sont pas des règles métier, juste du formatage d'affichage réutilisé à plusieurs endroits.

## Règles à respecter

1. **Jamais d'import direct de `data/` depuis `screens/`, `components/` ou `store/`.** Tout passe par `composition/repositories.ts` ou par les types du `domain/`.
2. **Un écran ne fait jamais d'appel réseau ni d'accès AsyncStorage.** Il dispatch une action, un thunk appelle un usecase, le usecase appelle le repository.
3. **Les composants de `components/` restent purement présentationnels.** Ils reçoivent des props déjà résolues (ex. `coverUrl: string`, pas `coverId: number` + un appel à `bookRepository` dans le composant). C'est à l'écran (qui dépend déjà de `composition/`) de résoudre l'URL avant de la passer.
4. **Nouvelle fonctionnalité = un usecase avant un thunk.** Si une action métier n'a pas de fonction dans `domain/usecases/`, elle ne va pas directement dans un thunk Redux.
5. **Nouvelle source de données = un nouveau dossier dans `data/` (types + mapping + client), jamais un changement d'interface `domain/`** sauf si le besoin métier change réellement. Exemples réels : `data/googleBooks/` et `data/bnf/` sont des replis ciblés de `findByIsbn` (pas des `BookRepository` complets), utilisés en interne par `OpenLibraryBookRepository` — jamais un appel `fetch` planqué dans un composant ou un thunk.
6. **Les types bruts d'une API externe (`OpenLibraryDoc`, `RawEdition`...) ne sortent jamais de `data/<source>/types.ts`.** Le mapping vers les entités du domain se fait dans `data/<source>/mappers.ts`.
7. **Un thunk Redux ne fait que : appeler un usecase, retourner son résultat.** La logique (dédoublonnage, fusion, validation) vit dans le usecase, pas dans le thunk ni dans le reducer. **Exception documentée** : `librarySlice.addBook`/`removeBook`/`patchLibraryEntry`/`toggleBookList` et `listsSlice.createList`/`renameList`/`deleteList` appellent aussi un second usecase de sauvegarde cloud best-effort (`syncLibraryEntry`/`removeLibraryEntryFromCloud`/`syncListEntry`/`removeListFromCloud`), jamais `await`é, dont le résultat n'alimente jamais la valeur retournée par le thunk — un effet de bord silencieux sur une écriture locale déjà terminée, pas une deuxième action métier du thunk. **Deuxième exception documentée** : `listsSlice.deleteList` dispatche aussi `librarySlice.setLibraryEntries` (une action simple, pas un usecase) pour répercuter dans l'autre slice le résultat de `deleteReadingList` (qui, lui, reste un seul usecase orchestrant deux repositories — voir sa doc) — une synchronisation d'état entre deux slices, pas une deuxième action métier. **Troisième exception documentée** : `authSlice.linkGoogleAccount` dispatche `librarySlice.setLibraryEntries` et `listsSlice.setLists` quand le usecase du même nom renvoie `status: 'switched'` (bascule vers un compte existant, voir la section Firebase Phase 3) — même raisonnement que la deuxième exception : `linkGoogleAccount` reste un seul usecase (qui orchestre 5 ports, voir sa doc), le thunk se contente de répercuter son résultat déjà calculé dans les deux autres slices.

## Conventions de code

- **UI et commentaires en français**, identifiants de code (variables, fonctions, types) en anglais — convention déjà en place dans tout le projet, à garder.
- Pas de `any` implicite ; types stricts partout, `interface` pour les ports (`BookRepository`, `LibraryRepository`), `type` pour les entités et le state.
- Les 4 listes par défaut (`DEFAULT_LIST_IDS.toRead`/`reading`/`read`/`liked`) et `EXCLUSIVE_STATUS_LIST_IDS` sont les seules constantes d'ids de listes ; ne pas les dupliquer, les importer depuis `domain/entities/ReadingList.ts`. Il n'y a plus de `ReadingStatus` dédié depuis la section "Listes de lecture publiques" — un livre appartient à des listes (`LibraryEntry.listIds: string[]`), pas à un statut figé.
- Style existant : composants fonctionnels, hooks, `StyleSheet.create` en bas de fichier, pas de librairie de style externe.

## Config plugins (`app.json` → `plugins`)

**Règle apprise à la dure (a cassé le build deux fois) :** un paquet ne va dans `app.json` → `plugins` que s'il exporte réellement un config plugin Expo (un fichier `app.plugin.js`, vérifiable dans `node_modules/<paquet>/package.json`). En lister un qui n'en exporte pas fait planter `expo start` avec des erreurs type `PluginError: Cannot find module './NativeStatusBarWrapper'`, même si le paquet est un module Expo par ailleurs légitime.

- `expo-status-bar` et `expo-image` **n'ont pas** de config plugin : ne jamais les mettre dans `plugins`.
- `expo-camera` **a** un vrai config plugin : il doit y rester, avec son message de permission caméra (`cameraPermission`).
- `@react-native-google-signin/google-signin` (Phase 3) **a** un vrai config plugin, confirmé via sa doc officielle — la forme simple (chaîne, sans options) suffit tant que `android.googleServicesFile`/`ios.googleServicesFile` pointent vers de vrais fichiers Firebase (voir section Firebase Phase 3). Ce paquet ne fonctionne que via `expo prebuild` + dev client, jamais dans Expo Go — voir plus bas.
- Avant d'ajouter un nouveau paquet natif à `plugins`, vérifier son `package.json`/ses fichiers plutôt que de deviner par analogie avec un autre paquet Expo.

## Firebase (Phase 1 : fondation)

Première brique du plan Firebase (doc Claude du projet, "firebase-social-plan") : connexion anonyme silencieuse au démarrage, aucun écran, aucune fonctionnalité visible encore. À savoir pour toute future phase qui touche à `data/firebase/` :

- **SDK JS modulaire (`firebase`, pas `@react-native-firebase`)** — seul choix compatible Expo Go, voir le plan pour la justification complète. Version minimale `^12.0.0` : les versions antérieures cassent la résolution des modules ES sous Expo.
- **`initializeAuth` + `getReactNativePersistence(AsyncStorage)`** (dans `firebaseApp.ts`), pas `getAuth` seul — sans ça, une session (y compris anonyme) ne survit pas au redémarrage de l'app, elle reste en mémoire uniquement.
- **`FirebaseAuthRepository` attend le premier `onAuthStateChanged`** avant de décider de créer un utilisateur anonyme (`ensureSignedIn`). La restauration d'une session persistée est asynchrone : lire `firebaseAuth.currentUser` immédiatement au démarrage peut renvoyer `null` même s'il existe déjà un utilisateur anonyme d'un lancement précédent, ce qui créerait un nouvel utilisateur (et perdrait le premier) à chaque démarrage si on ne l'attendait pas.
- **`.env`** — six variables `EXPO_PUBLIC_FIREBASE_*` (voir `env.dev.example`/`env.prod.example`, section Environnements ci-dessous), à récupérer dans la Firebase Console (app Web) ; l'authentification anonyme doit aussi être activée manuellement côté console (Authentication → Sign-in method → Anonymous) avant que `ensureSignedIn` fonctionne. Ce ne sont pas des secrets à proprement parler (SDK web, sécurité assurée par les règles Firestore), mais suivent la même convention hors-dépôt que `EXPO_PUBLIC_GOOGLE_BOOKS_API_KEY`.
- La liaison Google Sign-In et tout ce qui touche aux amis/au flux d'activité sont des phases ultérieures, pas encore implémentées — voir le plan pour la roadmap complète et les décisions encore ouvertes.

## Firebase (Phase 2 : sauvegarde cloud de la bibliothèque)

Deuxième brique du plan Firebase : chaque écriture sur la bibliothèque locale (ajout, changement de statut/note/aimé, suppression) est répliquée vers Firestore, en plus d'un passage de sauvegarde en masse au démarrage (`syncLibraryToCloud`, voir `App.tsx`) pour couvrir les entrées ajoutées avant l'existence de cette phase. Toujours en tâche de fond, jamais d'écran ni de blocage de l'UI :

- **À sens unique et best-effort côté écriture.** `syncLibraryEntry`/`removeLibraryEntryFromCloud` avalent silencieusement toute erreur (voir leur doc) : un échec de sauvegarde (hors ligne, base Firestore ou règles pas encore configurées côté console) ne doit jamais faire échouer une action locale ni la ralentir perceptiblement — d'où les appels en `void`, jamais `await`é, dans `librarySlice`. **Historique : à l'origine de cette phase, `LibraryRepository`/AsyncStorage restait l'unique source de vérité et rien ne lisait Firestore en retour — ce n'est plus le cas depuis "Firebase (Le serveur fait foi)" (voir plus bas), qui ajoute `fetchAll` et fait du serveur la référence.**
- **Champs synchronisés** : `title`, `authors`, `coverId`/`coverUrl`, `description`, `languages`, `workKeys`, `listIds`, `rating`, `note`, `addedAt`, `updatedAt` (`serverTimestamp()`) — voir `toFirestoreLibraryEntry`/`fromFirestoreLibraryEntry` dans `data/firebase/mappers.ts`. **`note` a rejoint les champs synchronisés depuis la section "Listes de lecture publiques"** (voir plus bas) — ce n'était PAS le cas en Phase 2 initiale (elle restait strictement locale) ; décision produit assumée pour cette section : la note devient visible par les autres utilisateurs au même titre que le reste, ces listes étant désormais en lecture publique. **`description`/`languages`/`workKeys`/`addedAt` ont rejoint les champs synchronisés depuis "Bascule vers un compte existant"** (section Firebase Phase 3) : sans eux, restaurer une bibliothèque depuis Firestore donnerait des entrées incomplètes (pas d'édition à recharger sur la fiche détail). Une entrée synchronisée avant ce changement n'aura ces champs qu'après sa prochaine écriture locale — pas de backfill rétroactif.
- **`?? null` systématique sur les champs optionnels** dans le mapper : Firestore refuse `undefined` comme valeur de champ (l'écriture échoue), contrairement à un objet JS ordinaire.
- **`initializeFirestore(app, { experimentalAutoDetectLongPolling: true })`** (dans `firebaseApp.ts`), pas `getFirestore` seul directement — le transport de streaming par défaut de Firestore (gRPC-Web/WebChannel) est peu fiable sur le fetch/XHR de React Native ; cette option bascule automatiquement sur du long-polling seulement quand c'est nécessaire. Même contrainte Fast Refresh que l'Auth : repli sur `getFirestore()` si `initializeFirestore()` a déjà été appelé sur cette app.
- **Configuration manuelle requise côté Firebase Console, dans CHACUN des deux projets (dev et prod)**, avant que la sauvegarde fonctionne réellement : créer une base Firestore (Firestore Database → Créer une base de données) et y coller les règles de `firestore.rules` (à la racine du dépôt — fichier de référence versionné, pas déployé automatiquement, pas de Firebase CLI dans ce projet). Sans ça, `upsertEntry`/`removeEntry` échouent silencieusement (best-effort, voir ci-dessus) — l'app reste pleinement utilisable, juste sans sauvegarde tant que ce n'est pas fait.
- **Les règles ont changé depuis la section "Listes de lecture publiques" (voir plus bas) : lecture désormais publique (tout utilisateur connecté), écriture toujours réservée au propriétaire.** Si `firestore.rules` a été collé dans la console AVANT cette section, il faut le recoller (nouvelle version) dans les deux projets Firebase — l'ancienne version (lecture restreinte au propriétaire) reste sinon active côté console malgré le fichier versionné.

## Firebase (Phase 3 : connexion Google)

Troisième brique du plan Firebase : liaison du compte Google de l'utilisateur à sa session anonyme existante (même `uid`, la bibliothèque cloud de la Phase 2 reste associée), depuis un unique écran Profil, à son initiative explicite — jamais automatique, conformément au principe UX de connexion non intrusive.

- **Sort du cadre Expo Go — lire l'avertissement en tête de ce fichier avant de toucher à quoi que ce soit ici.** Recherche documentée (Sept. 2026, doc Expo à jour + changelog `expo-auth-session`) : aucune lib de connexion Google (native ou via l'ancien `expo-auth-session/providers/google`, dont le proxy `auth.expo.io` a été entièrement retiré du SDK en juin 2023) ne fonctionne dans Expo Go. `@react-native-google-signin/google-signin` (lib choisie) nécessite un **dev client local** : `npx expo prebuild` génère les dossiers natifs `android/`/`ios/` (gitignorés, régénérés à la demande — jamais commités ni édités à la main), puis `npx expo run:android` / `npx expo run:ios` construisent et lancent l'app. Rien de tout ça n'utilise le service cloud EAS Build.
- **Deux nouveaux ports domain, jamais un seul mélangeant les deux responsabilités** : `GoogleIdentityProvider.signIn()` ne parle qu'à Google et retourne `{ idToken } | null` (`null` = annulé par l'utilisateur, pas une erreur) ; `AuthRepository.linkWithGoogle(idToken)` ne parle qu'à Firebase. Le usecase `linkGoogleAccount` orchestre les deux (plus 4 autres repos, voir plus bas). Si un jour une autre lib Google Sign-In remplace `@react-native-google-signin/google-signin`, seul `data/google/GoogleSignInProvider.ts` change.
- **`auth/credential-already-in-use` — bascule automatique vers le compte existant.** Ce compte Google est déjà lié à un AUTRE utilisateur Firebase (app réinstallée, ou compte déjà utilisé sur un autre appareil) : `FirebaseAuthRepository.linkWithGoogle` catch cette erreur Firebase brute et fait un `signInWithCredential` (pas un `linkWithCredential`) sur ce même credential, ce qui **abandonne la session anonyme courante et bascule l'app sur le compte Firebase existant**. Revirement volontaire par rapport à la décision initiale ("l'utilisateur est juste informé, pas de bascule ni de fusion", voir l'historique dans le plan Firebase, doc Claude du projet) : Google a déjà vérifié l'identité de la personne, la laisser bloquée sur un compte anonyme vide n'a plus de sens.
  - `linkWithGoogle` renvoie `{ profile, switchedToExistingAccount }` plutôt qu'un simple `UserProfile` — c'est à `switchedToExistingAccount` que le usecase `linkGoogleAccount` sait qu'il doit restaurer les données de ce compte existant.
  - **`linkGoogleAccount` orchestre alors la restauration complète** : `LibrarySyncRepository.fetchAll(uid)`/`ListSyncRepository.fetchAll(uid)` (nouvelles méthodes de lecture, ajoutées pour ce seul cas d'usage — voir leur doc, `data/firebase/mappers.ts` a aussi gagné `fromFirestoreLibraryEntry`/`fromFirestoreReadingList`, sens inverse de `toFirestore*`) lisent la bibliothèque/les listes de ce compte, puis `LibraryRepository.saveAll`/`ListRepository.saveAll` **remplacent** les données locales de la session anonyme abandonnée. Décision produit assumée : pas de fusion des deux bibliothèques (la session anonyme n'avait probablement rien d'important — sinon l'utilisateur n'aurait pas cherché à se reconnecter à un compte existant), on écrase.
  - **Cas limite couvert** : un compte existant plus ancien que "Listes de lecture publiques" (ou dont les listes n'ont jamais atteint Firestore) peut n'avoir aucune liste côté cloud — `linkGoogleAccount` retombe alors sur `seedDefaultLists` pour ne pas laisser l'utilisateur sans onglet dans `LibraryScreen`, et pousse ces listes nouvellement créées vers Firestore.
  - **Écran** : `ProfilScreen` affiche une alerte dédiée ("Compte retrouvé...") quand `linkGoogleAccount` renvoie `status: 'switched'`, pour que le changement de bibliothèque affichée à l'écran ne soit jamais silencieux.
  - Le mécanisme dépend d'un champ synchronisé plus riche qu'avant (`workKeys`/`description`/`languages`/`addedAt` rejoignent `listIds`/`rating`/`note` dans le document Firestore de chaque livre, et `createdAt` dans celui de chaque liste) — une entrée synchronisée *avant* ce changement n'aura ces champs qu'après sa prochaine écriture locale, pas de backfill rétroactif ; voir `data/firebase/mappers.ts`.
- **`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`** (`.env.*`, voir `env.dev.example`/`env.prod.example`) — le "Web client ID" que Firebase crée automatiquement en activant Google comme fournisseur (Authentication → Sign-in method → Google). C'est lui qui permet à `GoogleSignin.signIn()` de renvoyer un `idToken` exploitable par `GoogleAuthProvider.credential()` ; sans lui, `idToken` reste `null` — voir `GoogleSignInProvider`.
- **`google-services.<env>.json` / `GoogleService-Info.<env>.plist`** (racine du dépôt, jamais commités, voir `.gitignore`) — téléchargés depuis Firebase Console (Paramètres du projet → tes apps Android/iOS), un jeu par environnement. `scripts/use-env.js` les copie vers `google-services.json`/`GoogleService-Info.plist` (référencés depuis `app.json`) en même temps que `.env` — relancer `npx expo prebuild --clean` après un changement d'environnement pour que le projet natif reprenne le bon fichier.
- **Écran Profil (`ProfilScreen`, onglet dédié)** — seul déclencheur de `linkGoogleAccount`/`signOutUser`. Affiche l'état anonyme (pseudonyme généré, texte expliquant la sauvegarde entre appareils, bouton "Se connecter avec Google") ou lié (nom/photo Google + bouton "Se déconnecter"). `signOutUser` ne touche jamais à la bibliothèque locale : au redémarrage, `ensureSignedIn` recrée une session anonyme vierge.
- **`utils/anonymousPseudonym.ts` — pseudonyme du profil anonyme, purement cosmétique.** `generateAnonymousPseudonym(uid)` dérive un nom du style "Lecteur Nocturne 4821" à partir d'un hash déterministe de l'`uid` (aucun état, aucun appel réseau, aucune écriture Firebase) — stable pour un même utilisateur anonyme d'une session à l'autre. Volontairement **jamais écrit dans `UserProfile.displayName`** ni nulle part côté Firebase : ce champ reste réservé au vrai nom Google une fois lié (voir `domain/entities/UserProfile.ts`), pour ne pas confondre un pseudonyme purement local avec une identité retrouvable par d'autres utilisateurs — distinction qui comptera dès la Phase 4 (Amis).
- **`GoogleSignInProvider` — `require()` DANS les méthodes, jamais un `import` en haut de fichier. Leçon apprise à la dure (a planté l'app une fois).** `composition/repositories.ts` (donc `data/google/GoogleSignInProvider.ts`) est chargé par toute l'app, y compris en Expo Go (Phases 1/2/4+). Un premier essai avec un `import` classique de la lib, même en repoussant seulement `GoogleSignin.configure()` à plus tard, a fait planter l'app **au démarrage en Expo Go** avec `Invariant violation : TurbomoduleRegistry.getEnforcing(...): 'RNGoogleSignin' could not be found` : cette lib référence son module natif dès l'évaluation de son PROPRE code (son spec TurboModule appelle `TurboModuleRegistry.getEnforcing(...)` au chargement du fichier, pas seulement quand on appelle une de ses fonctions) — un simple `import` suffit à planter, avant même `configure()` ou l'écran Profil. Fix : `require('@react-native-google-signin/google-signin')` appelé À L'INTÉRIEUR de `GoogleSignInProvider.load()`, jamais en haut de fichier — un `require()` dans une méthode n'est exécuté qu'à l'appel de cette méthode (`signIn()`/`signOut()`), donc jamais tant que personne n'appuie sur "Se connecter avec Google". Si ça plante quand même à ce moment-là (utilisateur resté en Expo Go), l'erreur reste confinée au `try/catch` de l'écran Profil. **Toute future lib native ajoutée à `data/` doit suivre ce même principe** si elle est censée rester optionnelle vis-à-vis d'Expo Go.

## Firebase (Le serveur fait foi)

Revirement architectural par rapport aux Phases 1/2 (voir le plan Firebase, doc Claude du projet, section "Le serveur fait foi" pour l'historique de la décision) : **Firestore devient la source de vérité de la bibliothèque et des listes ; `LibraryRepository`/`ListRepository` (AsyncStorage) ne sont plus qu'une copie de secours locale**, affichée instantanément (rapide, marche hors ligne) puis rafraîchie en arrière-plan depuis le serveur.

- **Deux déclencheurs seulement, jamais de temps réel/listener continu** — décision produit assumée pour limiter le coût réseau : au démarrage de l'app (`App.tsx`) et à chaque fois qu'un écran de l'onglet Bibliothèque reprend le focus (`LibraryScreen.tsx` ET `ListDetailScreen.tsx`, via le hook partagé `useLibrarySync` — voir plus bas la section "Listes de lecture publiques" pour pourquoi ce mécanisme vit désormais dans un hook plutôt que dans `LibraryScreen` seul). Rien d'autre ne déclenche ce rafraîchissement (pas de polling, pas de listener `onSnapshot`).
- **`refreshLibraryFromServer`/`refreshListsFromServer`** (nouveaux usecases) : lisent Firestore via `fetchAll(uid)`, puis **remplacent** (jamais de fusion) la copie locale via `LibraryRepository.saveAll`/`ListRepository.saveAll` en cas de succès. Best-effort et silencieux, même philosophie que `syncLibraryEntry` : `uid` absent ou Firestore injoignable/en erreur → retournent `null`, et les thunks correspondants (`librarySlice.refreshLibrary`/`listsSlice.refreshLists`) laissent alors `entries`/`lists` inchangés dans `extraReducers` plutôt que d'écraser l'écran avec rien. Jamais de spinner ni d'alerte pour un échec de ce rafraîchissement — voir le principe UX de connexion non intrusive.
- **Ordre "push puis pull", partout, jamais un pull seul — bug corrigé.** `syncLibraryToCloud`/`syncListsToCloud` (sauvegarde en masse du local vers le cloud) sont toujours **attendus** avant de dispatcher `refreshLibrary`/`refreshLists`, aussi bien au démarrage (`App.tsx`) qu'à chaque focus d'un écran utilisant `useLibrarySync` (`LibraryScreen.tsx`, `ListDetailScreen.tsx`). Sans cet ordre, un rafraîchissement pouvait lire une version serveur en retard et écraser des changements locaux pas encore remontés (`saveAll` remplace toute la bibliothèque locale) — **bug réellement rencontré** : `addBook`/`toggleBookList` déclenchent leur sauvegarde cloud en tâche de fond sans jamais l'attendre (voir plus bas), donc rien ne garantissait qu'elle ait atteint Firestore avant qu'un focus de l'onglet Bibliothèque juste après ne déclenche un pull qui écrasait le livre tout juste ajouté/aimé avec une version serveur encore sans lui. D'abord corrigé partiellement (push seulement au démarrage), puis étendu au focus de l'onglet une fois ce symptôme remonté. Ces deux thunks de sauvegarde en masse ne rejettent jamais (erreurs avalées par `syncLibraryEntry`/`syncListEntry`), donc les attendre ne bloque jamais l'app hors ligne, à aucun des deux déclencheurs.
- **Garde-fou anti-course `revision`/`baselineRevision`/`shouldApply` — deuxième bug corrigé, le push-avant-pull ci-dessus ne suffisait pas seul.** Même avec cet ordre, le symptôme persistait : ajouter/aimer un livre puis revenir presque immédiatement sur l'onglet Bibliothèque pouvait encore le faire disparaître. Cause réelle : l'ajout/like se produit sur un AUTRE écran, et sa mise à jour de Redux (via le `.fulfilled` du thunk `addBook`/`toggleBookList`) peut ne pas encore avoir atterri au moment où le cycle push+pull de cet écran démarre (ou même pendant qu'il tourne, le `fetchAll` prenant un aller-retour réseau) — ce cycle part alors sans cette mutation, le pull revient avec une version serveur qui ne l'a pas non plus, et l'écrase quand même.
  - `LibraryState`/`ListsState` ont chacun gagné un compteur `revision: number`, incrémenté dans `extraReducers` à chaque mutation LOCALE (`addBook`/`removeBook`/`patchLibraryEntry`/`toggleBookList`/`setLibraryEntries` pour la bibliothèque ; `createList`/`renameList`/`deleteList`/`setLists` pour les listes) — jamais par `fetchLibrary`/`fetchLists` (chargement initial) ni par `refreshLibrary`/`refreshLists` eux-mêmes (ce n'est pas une mutation locale, c'est l'application d'un résultat serveur déjà validé).
  - L'appelant (`App.tsx`, `useLibrarySync`) lit ce compteur (`store.getState().library.revision`/`...lists.revision`) **avant** de lancer le push, et le passe en argument à `refreshLibrary`/`refreshLists` (`baselineRevision`). Le thunk le transmet à `refreshLibraryFromServer`/`refreshListsFromServer` sous forme d'une fonction `shouldApply()` qui, une fois `fetchAll` terminé, relit la revision CourANTE et la compare à `baselineRevision`. Si elles diffèrent, une mutation locale a eu lieu quelque part dans la fenêtre push+fetch : le résultat est jeté (ni `saveAll` ni écrasement de Redux), le prochain déclencheur rattrapera le coup avec cette mutation déjà incluse.
  - Dans `useLibrarySync` (`src/hooks/useLibrarySync.ts`, extrait de `LibraryScreen.tsx` le 05/10/2026 pour être partagé avec `ListDetailScreen.tsx` — voir "Listes de lecture publiques" plus bas), la lecture de la revision se fait via `store.getState()` importé directement (comme dans `App.tsx`), pas via `useAppSelector` : le `useCallback` passé à `useFocusEffect` a des dépendances volontairement stables (`[dispatch]`, pour ne se déclencher qu'au focus) qui capturerait sinon une valeur figée au premier rendu, jamais rafraîchie.
- **`fetchAll` n'est plus réservée à la restauration d'un compte existant** (voir "Firebase (Phase 3 : connexion Google)") : c'est désormais le mécanisme de lecture générique de `LibrarySyncRepository`/`ListSyncRepository`, utilisé par ces deux cas d'usage à la fois.
- **N'affecte pas la sauvegarde au fil de l'eau** (Phase 2, ci-dessus) : chaque écriture locale continue d'être répliquée vers Firestore immédiatement, en best-effort. Le rafraîchissement décrit ici ne fait que faire circuler l'information dans l'autre sens, aux deux moments précis listés plus haut.
- **Id Firestore invalide pour les livres Open Library — troisième bug corrigé, PRÉ-EXISTANT DEPUIS LA PHASE 2, resté invisible jusqu'ici.** `LibraryEntry.id`/`Book.id` est la clé "œuvre" du catalogue Open Library (ex. `/works/OL136524W`), avec un `/` intégré — jamais un identifiant "plat". `FirestoreLibraryRepository.upsertEntry`/`removeEntry` l'utilisaient tel quel comme segment de chemin Firestore (`users/{uid}/library/{bookId}`), ce que Firestore refuse (`/` est un séparateur de chemin, pas un caractère valide dans un id) : `FirebaseError: Invalid document reference ... must have an even number of segments`. Comme `syncLibraryEntry` avale silencieusement toute erreur (best-effort, voir sa doc), **aucun livre Open Library — donc la quasi-totalité des livres de l'app — n'avait jamais été réellement sauvegardé sur Firestore depuis la Phase 2**, et ce bug serait resté invisible sans l'ajout des logs `[Readr][debug sync]` pendant le travail sur "Le serveur fait foi" ci-dessus, qui l'a enfin fait apparaître dans la console. Fix dans `FirestoreLibraryRepository.ts` : un helper `toFirestoreDocId(entryId)` (`encodeURIComponent`) encode l'id en segment de chemin Firestore valide à l'écriture (`upsertEntry`/`removeEntry`), et `fetchAll` applique le `decodeURIComponent` symétrique sur `d.id` pour reconstruire l'id d'origine exact. L'id applicatif (`LibraryEntry.id`) ne change pas, seul l'id DU DOCUMENT Firestore diffère de lui. Les listes de lecture (`FirestoreListRepository`) ne sont PAS concernées : leurs ids viennent de `utils/generateId.ts`, un schéma déjà sûr pour Firestore.

## Listes de lecture publiques

Généralise les 4 listes historiques (À lire/En cours/Lu/Aimés — auparavant un `status: ReadingStatus` figé + un `liked?: boolean` indépendant sur `LibraryEntry`) en `ReadingList` ordinaires, au même titre que les listes perso que l'utilisateur peut créer. Réponse à une demande explicite du porteur du projet : que ces listes (et les livres dedans) soient accessibles hors-ligne ET visibles par d'autres utilisateurs.

- **`domain/entities/ReadingList.ts`** — `{ id, name, isDefault, exclusive, createdAt }`. `isDefault` marque les 4 listes créées à la création du compte (non supprimables/renommables, appliqué dans `renameReadingList`/`deleteReadingList` — no-op silencieux sur une liste par défaut). `exclusive` marque les 3 listes de statut (À lire/En cours/Lu, `EXCLUSIVE_STATUS_LIST_IDS`) : ajouter un livre à l'une l'enlève automatiquement des deux autres (voir `toggleBookList`) — **décision produit assumée : ce trio reste mutuellement exclusif comme avant ce refactor**, contrairement à "Aimés" et aux listes perso qui n'ont jamais cette contrainte (cumulables entre elles et avec n'importe quel statut). `DEFAULT_LIST_IDS` fixe les ids des 4 listes par défaut, identiques en local et dans Firestore.
- **`LibraryEntry.listIds: string[]`** remplace `status`/`liked` — un livre appartient à 0+ listes. `addBookToLibrary(repo, entries, book, initialListId = DEFAULT_LIST_IDS.toRead)` : l'ajout initial va dans une seule liste (par défaut "À lire", ou "Aimés" depuis la bulle cœur si le livre n'est pas encore dans la bibliothèque). `toggleBookList(repo, entries, allLists, bookId, listId, add)` gère l'ajout/retrait à UNE liste, avec la règle d'exclusivité ci-dessus — c'est lui qui remplace l'ancien `updateLibraryEntry({ patch: { status } })`/`{ liked }`. `updateLibraryEntry` ne gère plus que `rating`/`note`.
- **Seedées à la création du compte** (`seedDefaultLists`, dispatché depuis `App.tsx` au démarrage, comme `fetchLibrary`/`ensureSignedIn`) : idempotent — s'il existe déjà des listes localement (compte déjà initialisé, y compris avant l'existence de cette fonctionnalité), ne fait rien. "Création du compte" au sens produit, mais implémenté comme "aucune liste locale encore" plutôt que sur un vrai événement Firebase, pour rester robuste sans écran ni logique de migration dédiée.
- **Migration douce des anciennes entrées locales** (`AsyncStorageLibraryRepository.getAll`, voir sa doc) : une entrée sans `listIds` (ancien format `status`/`liked`) est convertie silencieusement à la lecture, une seule fois, sans écran ni action utilisateur.
- **Listes perso** : `createReadingList`/`renameReadingList`/`deleteReadingList` (jamais `isDefault`/`exclusive`). `deleteReadingList` orchestre `ListRepository` + `LibraryRepository` dans un seul usecase (même esprit que `linkGoogleAccount`, qui orchestre 5 ports domain — voir la section Firebase Phase 3, "Bascule vers un compte existant") : supprimer une liste retire aussi son id de `listIds` sur tous les livres concernés, jamais les livres eux-mêmes. Ids générés par `utils/generateId.ts` (pas de dépendance `uuid`/`nanoid` pour un besoin aussi ponctuel).
- **Stockage local** : `AsyncStorageListRepository` (`ListRepository`, clé `@readr/lists`), même pattern que `AsyncStorageLibraryRepository` — accès complet hors-ligne, comme la bibliothèque.
- **Stockage cloud, LECTURE PUBLIQUE — décision produit à ne pas prendre à la légère** : `FirestoreListRepository` (`ListSyncRepository`, `users/{uid}/lists/{listId}`) et `FirestoreLibraryRepository`/`users/{uid}/library/{bookId}` (déjà là depuis la Phase 2, désormais avec `listIds`+`note` en plus, voir section Phase 2 ci-dessus) sont en **lecture publique** côté `firestore.rules` (`allow read: if request.auth != null`, sans restriction au propriétaire) — n'importe quel utilisateur connecté (même anonyme) peut lire la bibliothèque et les listes de n'importe qui. L'écriture reste réservée au propriétaire (`request.auth.uid == uid`, inchangé). **`firestore.rules` doit être recollé manuellement dans les deux projets Firebase Console** si l'ancienne version (lecture restreinte) y était déjà — un fichier versionné dans le dépôt ne se déploie pas tout seul (pas de Firebase CLI ici).
- **Ce qui n'est PAS construit à ce stade** : aucun écran ne permet de parcourir la bibliothèque ou les listes d'un AUTRE utilisateur — ces règles ouvrent seulement la donnée en lecture, sans mécanisme de découverte/amis. Ce sera la Phase 4 ("Amis"), pas encore conçue (friend-discovery, granularité de confidentialité par liste — voir le plan Firebase, doc Claude du projet). Ne pas anticiper cette UI par avance.
- **`LibraryScreen`/`ListDetailScreen` — UI "playlist" façon Spotify (refonte du 05/10/2026), remplace l'ancienne disposition à onglets horizontaux + grille inline.** `LibraryScreen` ne montre plus qu'une colonne verticale de lignes "playlist" (`ListPlaylistRow`), une par liste (`state.lists.lists`, même ordre fixe qu'avant : les 4 par défaut puis les listes perso par date de création) ; chaque ligne affiche une vignette (couverture du livre le plus récemment ajouté à cette liste, ou à défaut une icône + couleur sémantique par liste par défaut — `bookmark`/`book`/`checkmark-done`/`heart` — ou une icône générique + couleur dérivée d'un hash stable de l'id pour une liste perso), le nom, le nombre de livres, et un chevron. Taper une ligne navigue vers `ListDetailScreen` (nouvel écran de la pile, `LibraryStackParamList.ListDetail`), qui affiche la grille de livres de cette seule liste (même logique de tri date/note qu'avant) ; son en-tête affiche le nom de la liste et, pour une liste non-`isDefault`, un bouton de suppression (`navigation.setOptions` dans un `useLayoutEffect`, avec confirmation `Alert` rappelant que les livres restent dans la bibliothèque). Bouton "+" pour créer une liste perso reste sur `LibraryScreen` (nom saisi inline, pas de modal dédiée). **Raison du changement** : l'ancienne disposition (onglets horizontaux + grille sous les onglets, le tout dans un seul écran) avait un espacement qui se comportait mal à l'usage ; cette refonte en deux écrans se prête aussi mieux à l'ajout futur de listes perso (une ligne de plus, sans rien à adapter dans la mise en page). **`StatusSegmented`** (sur `BookDetailScreen`, inchangé par cette refonte) garde son UI de segmented control à 3 valeurs fixes, manipulant un id de liste générique (`value: string`) plutôt qu'un `ReadingStatus` dédié. **`BookDetailScreen`** garde sa section "Mes listes" (chips togglables pour les listes perso) — vide avec un texte d'invite tant que l'utilisateur n'a créé aucune liste perso.
- **`useLibrarySync` (`src/hooks/`) — mécanisme de rafraîchissement serveur ("Le serveur fait foi") extrait de `LibraryScreen` pour être partagé avec `ListDetailScreen`.** Avant cette refonte, le push-puis-pull avec garde-fou anti-course (voir section Firebase "Le serveur fait foi" plus bas) vivait uniquement dans le `useFocusEffect` de `LibraryScreen`. Avec `ListDetailScreen` comme écran séparé, on peut tout aussi bien revenir directement dessus (depuis `BookDetailScreen`, après un ajout/like) sans repasser par `LibraryScreen` — sans ce hook appelé aussi sur `ListDetailScreen`, le livre tout juste ajouté pourrait sembler disparaître dans CET écran précis, répétant exactement le bug déjà corrigé une fois pour `LibraryScreen` seul (voir plus bas). Les deux écrans appellent simplement `useLibrarySync()`, qui encapsule le `useFocusEffect` (push `syncLibraryToCloud`/`syncListsToCloud`, puis pull `refreshLibrary`/`refreshLists` avec `baselineRevision` capturé via `store.getState()`).

## Recommandations collaboratives (Cloud Functions)

Réponse à une demande explicite du porteur du projet d'améliorer l'onglet Découvrir, avec usage de Firebase Cloud Functions explicitement autorisé (voir le plan Firebase, doc Claude du projet, section "Recommandations collaboratives", pour l'arbitrage produit complet entre "tendance globale", "collaboratif entre lecteurs", les deux, ou rester côté client — le collaboratif a été retenu). Première utilisation de Cloud Functions dans ce projet : introduit `firebase.json` et un codebase Node/TypeScript séparé (`functions/`), en dehors du graphe domain/data/composition de l'app (`functions/` a son propre `package.json`/`tsconfig.json`, importe le SDK Admin, jamais le SDK client).

- **Principe : "les lecteurs qui ont aimé X ont aussi aimé Y", calculé sur TOUS les utilisateurs de l'app, pas seulement des amis.** Rendu possible sans attendre la Phase 4 ("Amis", pas encore conçue) parce que "Listes de lecture publiques" (ci-dessus) a déjà rendu `users/{uid}/library/*` lisible par n'importe quel utilisateur connecté — "les lecteurs" ici veut dire "toute la base", pas "mes amis". Ça couvre une partie de ce qui était envisagé comme Phase 7 ("Recommandations sociales") dans le plan Firebase, en avance sur la Phase 4.
- **`domain/repositories/BookStatsRepository.ts`** — nouveau port, `getRelatedBooks(bookId: string): Promise<Book[]>`. Implémenté par `data/firebase/FirestoreBookStatsRepository.ts`, qui lit `bookStats/{bookId encodé}` et retourne `[]` en cas d'erreur/absence (best-effort, même philosophie que `syncLibraryEntry` — une recommandation manquante n'est jamais une erreur visible). Câblé dans `composition/repositories.ts` (`bookStatsRepository`).
- **Collection `bookStats/{bookId}`, écrite UNIQUEMENT par la Cloud Function (SDK Admin, qui ignore les règles Firestore de toute façon).** `firestore.rules` : `allow read: if request.auth != null; allow write: if false;` — lecture publique comme `library`/`lists`, mais aucune écriture cliente possible même en théorie. Chaque document contient `relatedTo: [{ id, title, authors, coverId, coverUrl, description, languages, workKeys, count }]` (au plus 8, triés par `count` décroissant) et `updatedAt`.
- **Id de document Firestore encodé — même contrainte, même fix que `FirestoreLibraryRepository`** (voir section Firebase Phase 2 ci-dessus, "Id Firestore invalide pour les livres Open Library") : l'id applicatif d'un livre contient un `/` (clé "œuvre" Open Library), invalide comme segment de chemin Firestore. Appliqué dès l'écriture dans `functions/src/recomputeBookStats.ts` (`encodeURIComponent` sur l'id du document `bookStats`, `decodeURIComponent` à la lecture des docs `library` via `collectionGroup`) et symétriquement à la lecture côté app dans `FirestoreBookStatsRepository`. Appris une fois, appliqué par précaution dès la conception plutôt que redécouvert.
- **`functions/src/recomputeBookStats.ts` — l'algorithme.** Une seule lecture `db.collectionGroup('library').get()` (déjà publique en lecture, pas de filtre donc pas d'index composite requis), regroupée par utilisateur ; ne garde que les entrées dans la liste "Aimés" ou "Lu" (`listIds` contient `default-liked` ou `default-read`) ; compte les co-occurrences par paire de livres **au sein d'un même utilisateur seulement** (jamais entre deux comptes différents) ; écrit pour chaque livre concerné ses 8 associations les plus fréquentes. Tout en mémoire (`Map`, pas de pagination/streaming) — assumé explicitement non scalable au-delà de l'échelle personnelle/portfolio de ce projet (au plus quelques dizaines d'utilisateurs et de livres), pas la peine de complexifier pour un volume qui n'existera pas. Batches d'écriture Firestore limités à 450 (marge sous la limite de 500/batch).
- **Planifiée, pas déclenchée en temps réel — même principe déjà acté pour "Le serveur fait foi" (deux déclencheurs précis plutôt que du temps réel).** `functions/src/index.ts` exporte `scheduledRecomputeBookStats` (`onSchedule('every 24 hours', ...)`, Gen 2) : un recalcul complet à chaque like/ajout (`onDocumentWritten`) coûterait une passe sur TOUTE la bibliothèque de tout le monde à chaque écriture d'un seul utilisateur, pour un gain de fraîcheur qui ne compte pas ici. `recomputeBookStatsManually` (`onRequest`, protégée par un secret partagé `RECOMPUTE_SECRET` — pas un vrai besoin de sécurité, juste pour éviter qu'un appel découvert par hasard ne déclenche des recalculs répétés) permet de tester sans attendre le passage planifié.
- **`getRecommendations` (usecase) — nouvel ordre de groupes et déduplication inter-groupes.** Signature étendue : `getRecommendations(repo, bookStatsRepo, libraryEntries)`. Groupes générés dans cet ordre : collaboratif (`collaborativeRecommendationGroups`, au plus `MAX_COLLAB_GROUPS = 2` groupes de `MAX_COLLAB_CANDIDATES = 5` candidats chacun, basés sur les livres "aimés"/"lus" de l'utilisateur) → auteur-lu → auteur-aimé → genre. Un seul `excludedIds: Set<string>` (renommé depuis `ownedIds`, initialisé avec les ids déjà dans la bibliothèque) est enrichi au fil des 4 étapes, pour qu'un même livre ne puisse jamais apparaître dans deux groupes différents du même écran Découvrir.
- **Prérequis manuels, à faire une fois par environnement (dev puis prod) — Claude ne peut pas les effectuer.** Passer les deux projets Firebase (dev et prod) du plan Spark (gratuit) au plan Blaze (payant à l'usage, carte bancaire requise dans la Console Firebase) : les Cloud Functions n'existent pas sur Spark. L'usage de cette fonctionnalité reste dans le quota toujours-gratuit de Blaze à l'échelle de ce projet, mais l'upgrade de plan lui-même doit être fait manuellement par le porteur du projet. Puis installer la CLI Firebase (`npm install -g firebase-tools`), `firebase login`, `firebase use --add` pour enregistrer les alias dev/prod dans `.firebaserc`, `cd functions && npm install && cp .env.example .env` (avec une vraie valeur de `RECOMPUTE_SECRET`), et `firebase deploy --only functions` pour chaque environnement. `firebase.json` rend aussi `firestore.rules` déployable en CLI (`firebase deploy --only firestore:rules`) — une nouveauté par rapport à la Phase "Listes de lecture publiques" ci-dessus, qui documentait encore le copier-coller manuel dans la Console comme seule option.

## Environnements (dev / prod)

Deux projets Firebase distincts, jamais mélangés — le projet dev sert aux tests (utilisateurs anonymes jetables), le projet prod à l'usage réel de l'app :

- **`.env.dev` / `.env.prod`** — un fichier par environnement, jamais commité (voir `.gitignore`), contenant les vraies valeurs `EXPO_PUBLIC_FIREBASE_*` du projet Firebase correspondant (+ la clé Google Books, identique dans les deux). Templates : `env.dev.example` / `env.prod.example` à la racine — nommage sans le préfixe `.env` par contrainte de l'environnement de dev à distance (les outils de pont vers la machine de l'utilisateur refusent d'écrire tout fichier dont le nom commence par `.env`, sauf `.env.example` explicitement ; sans impact sur l'usage normal en local, l'utilisateur peut créer `.env.dev`/`.env.prod` normalement).
- **`.env`** — le seul fichier qu'Expo charge réellement (`npx expo start`). Jamais rempli à la main : c'est une copie de `.env.dev` ou `.env.prod`, régénérée par `scripts/use-env.js` via `npm run env:dev` / `npm run env:prod` (ou `npm run start:dev` / `npm run start:prod`, qui enchaînent bascule + `expo start -c`).
- **Pourquoi un script maison plutôt que `.env.development`/`.env.production` + `NODE_ENV`** (mécanisme intégré d'Expo) : ce mécanisme ne s'active que pour `expo export`/EAS Build (`NODE_ENV=production` forcé) — jamais pour `expo start`, seul mode utilisé par ce projet (Expo Go, pas de build). Le déclencher manuellement pour `expo start` est explicitement déconseillé par la doc Expo (effets de bord sur d'autres outils qui lisent `NODE_ENV`, ex. `npm install` qui sauterait les devDependencies). `scripts/use-env.js` (copie de fichier, cross-platform, aucune dépendance) est l'approche que la doc Expo recommande elle-même pour ce cas (`expo start` sans EAS).
- **`EXPO_PUBLIC_APP_ENV`** (`development`/`production`, dans chaque fichier `.env.*`) — juste un repère : loggé au démarrage par `firebaseApp.ts` (avec le `projectId` actif) pour vérifier d'un coup d'œil dans la console Metro/Expo Go qu'on n'est pas pointé sur le mauvais projet avant de tester quoi que ce soit qui écrit des données. N'est lu nulle part ailleurs dans le code — ce n'est pas un flag qui change le comportement de l'app, seulement un log.

## Dossiers obsolètes

`src/api/` et `src/storage/` sont l'ancienne implémentation (avant le passage à Clean Architecture + Redux). Leurs fichiers sont vidés et commentés ; rien ne les importe. Ils peuvent être supprimés du disque — Claude ne peut pas le faire à distance sur cet environnement, donc ça reste une suppression manuelle.

`src/data/googleBooks/` a été un temps désactivé (quota anonyme Google Books trop bas, remplacé par `src/data/bnf/`), puis réactivé avec une vraie clé API — il n'est **plus** obsolète, voir la section Architecture ci-dessus.

`src/components/FormatBadge.tsx` (et `accentForFormat` dans `theme.ts`) ne sont plus utilisés depuis que la fiche livre affiche les éditeurs (`Edition.publisher`) en texte simple plutôt que les formats en badges colorés (voir README, section Choix techniques). Laissés en place plutôt que supprimés, au cas où des badges de format seraient réintroduits ailleurs.

## Avant de proposer un changement de structure

Ce projet sert aussi de pièce de portfolio technique : la séparation en couches est volontaire et doit rester lisible même si l'app reste petite. Ne pas la simplifier "pour aller plus vite" sans en parler d'abord.
